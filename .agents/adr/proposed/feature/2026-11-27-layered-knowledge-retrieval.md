# ADR: Knowledge is read in three layers, with history as a separate cold path

Status: proposed — no view level, span hydration or layer return shape exists; the model is a fixed core of the refactor
Date: 2026-11-27
Scope: The read model for Knowledge documents, the shape of each layer's return value, handle-based hydration, and the boundary of the history path
Related: `2026-11-27-derived-knowledge-indexes.md`, `2026-11-27-hybrid-knowledge-index-strategy.md`, `2026-11-27-stable-section-identity-and-drift.md`, `2026-11-27-spoke-knowledge-protocol-gaps.md`

## Problem

Knowledge entries enter the context pack whole today, in stored order, cut at a token budget (`recall_context`, `crates/mindcore-sqlite/src/knowledge.rs`). That is affordable while documents are small and the collection is short. It stops being affordable when a Mind holds hundreds of dense documents: the pack either carries documents the task does not need or overflows the budget and truncates the one it does, and a whole document spends most of its tokens on text that no decision depends on.

Shrinking documents into fixed chunks trades one failure for another: BM25 statistics on short chunks are unreliable — the current implementation computes IDF over one authorised page — and a chunk has no outline, so the reader cannot see whether the document as a whole contradicts it.

There is a third problem. History and current text have different semantics: history is immutable, appendix-shaped, and read to answer "why"; current text is what a task must obey. Mixing them in one ranked surface makes a stale revision compete with a live rule, and it puts history into an index that is meant to be disposable.

The three layers are a fixed core of this refactor, not an open question. What is open is their return shape and how a span is addressed, and that is what this record fixes.

## Proposal

A Knowledge read will have three current layers and one separate history path. **They may exist for any Knowledge node — a collection, domain, folder or document — not only for a document.**

- **L0 — navigation card.** A card will carry the node kind (collection, domain, folder or document), its canonical path, its declared summary, triggers and symbols, and for a document its stable id, version, section count and size. A container card will be composed from child versions and path-derived folder metadata, not from an independent commit. It will carry no body prose. L0 will be the coarse pruning layer.
- **L1 — bounded navigation or outline, by node kind.** For a **container**, L1 will be bounded child navigation: child ids and paths, key constraints and path-derived folder metadata, without enumerating bodies or implicitly traversing the whole subtree. For a **document**, L1 will be the section outline: every section's id, title, kind, position, byte range and span digest, plus a complete **hydration handle** that pins the document version, and the declared invariants, constraints and interface signatures and each section's byte size. A client holding only the L1 response can hydrate without another read. L1 will be the first-pass decision layer, bounded by a declared budget and carrying no prose beyond the declared lines.
- **L2 — exact leaf content.** A span will be requested by a handle: collection, document, version, section id, byte range and span digest. Hydration will return exactly those bytes and will verify them against the digest. A handle will pin the version it was created from and will never silently resolve to a newer version. A pinned hydration will not be a current view: it will not answer `ViewStale`, and it will return the pinned bytes, or not found when the caller may not see that document version, even after the document has moved or been deleted. `ViewStale` will apply only to a view opened at a head and compiler version that has since moved, which a caller reopens. A container will never be hydrated as an implicit subtree of leaf content. An `l2` request that names a container rather than a document and section will be refused with a named `VIEW_LAYER_UNSUPPORTED` reason, and `2026-11-27-spoke-knowledge-protocol-gaps.md` owns the reachable container-view entry.
- **Deterministic container views and optional abstract.** A container view will require a validated `scope_id` (or the existing admitted Scope); a caller with multiple Minds must name it, and a missing scope is refused with no default. Container L0/L1 will then be derived deterministically from canonical paths and the **visible child documents under that scope**, not from an unrestricted child set or an independent folder descriptor. Before navigation, summary or abstract generation, the projection will compute the visible child set and an **authorization fingerprint** of the admitted scope; that set and fingerprint will be part of the **server-side** cache identity only, so a cache prewarmed at higher privilege cannot serve a lower-privilege view and no response will contain the fingerprint. No model call will be required for availability or baseline ranking. An optional model abstract may be returned as a separate derived artifact with model id/version, prompt id/version and input digest, and the deterministic container view will be its fallback without reindexing under the same active embedding identity. It will never silently replace the deterministic view (`2026-11-27-derived-knowledge-indexes.md` and `2026-11-27-canonical-knowledge-format.md` own its derivation and cache).
- **Visibility is per item and per version.** Every layer's item will be admitted before it is returned: the document's visibility will be decided under the caller's scope for the requested version, a history item at its own revision, and a cross-domain reference for each actual owner. A history diff will require **both** compared versions to be visible; if either is hidden, the diff will answer as not found rather than disclose one side. A hidden item will answer exactly as an absent one, so its existence does not leak.
- **Only the visible body will leave the layer.** L0, L1 and L2 payloads, previews and retrieval results will carry the visible summary, navigation or outline body and the minimum stable identifiers needed for the next step. They will not carry the generator component, freshness counters, source metadata, review state or any other internal metadata. Raw metadata will be reachable only through the separate admin/debug read defined in `2026-11-27-spoke-knowledge-protocol-gaps.md`, which a normal read scope cannot call, and the embedding input will be the same visible projection (`2026-11-27-hybrid-knowledge-index-strategy.md`).
- **L3 — history, separate.** History, log and diff will be a cold path keyed by document and version, read only on request. Shared or non-primary history will be read through the qualified history receiver defined in `2026-11-27-spoke-knowledge-protocol-gaps.md`, under a validated Mind scope and inside that scope's admitted read set and disclosure rule; a missing scope is refused, and an unqualified history read remains the primary-Mind path. No historical blob will enter the lexical or vector index, and no history will be mixed with Fact history.
- **Escalation will be caller-driven.** L0 will not imply L1, and L1 will not imply L2. Each response will carry the domain, document, version, section and byte size, so a caller can budget before asking for more. A pack will report what it included and what it truncated.
- **Ordering.** L0 candidates will come from document-level ranking, not from a section list (`2026-11-27-hybrid-knowledge-index-strategy.md`), so a long document cannot crowd out a document whose summary or symbols match strongly. Section search will run only inside the documents L0 and L1 kept, with a per-document cap on returned sections.

## Alternatives considered

- **Keep whole-entry packing (the status quo).** Cheapest to ship, no read path change. Rejected because cost per accepted task grows with the collection, no citation is possible, and a document that is mostly irrelevant displaces one that matters.
- **Flat fixed-size chunks with lexical retrieval.** Simple and cheap. Rejected: chunk statistics are unreliable, a chunk cannot be checked against its document's constraints, and hydration would return fragments no section owns.
- **Model-generated summaries as the authoritative L0/L1 view or as part of the write gate or baseline ranking.** Rejected: nondeterministic output, a summary that drifts with no event, a per-write model cost, and no stable cache key. The optional model-generated abstract remains allowed only as the separate derived artifact described in the Proposal, with model/prompt/input provenance and deterministic fallback; the deterministic L0/L1 view will always come from declared metadata, AST and compiler version.
- **Always hydrate L2.** Maximum fidelity. Rejected: it is the current cost problem with more round trips.
- **One unified surface including history.** Rejected: a historical revision would compete with a live rule in ranking, and the index would stop being disposable because pruning would change results.
- **Fixed-length byte windows over the document.** Rejected: windows cross section boundaries, so a handle cannot name an owner and drift cannot be attributed.
- **A single "view level" that returns a fully packed context.** Rejected: it hides where the tokens went and makes truncation invisible to the caller.

## Acceptance criteria

- A container L0/L1 response will be bounded child navigation and key constraints; a document L1 response will be the section outline, constraints and interfaces. L2 will return exact leaf spans only.
- An L0 response will contain no body prose; an L1 response will contain no prose beyond declared constraint, invariant and signature lines.
- A container's navigation and summary will be derived from child versions and path-derived folder metadata with no independent container commit; an optional abstract will carry model, prompt and input digest and will never be required for availability or baseline ranking.
- A container view will require a validated scope; the same principal reading one shared container with two Mind scopes will receive each scope's authorized child subset, and a missing scope will be refused with no default.
- Before a container view or abstract is generated, the visible child set and authorization fingerprint will be computed and included only in its server-side cache identity; no response will contain the fingerprint, and a cache prewarmed at high privilege will leave the lower-privilege path, count, summary and constraint unchanged when high-only children are added or removed.
- A container L2 request will answer with a named refusal, not leaf content. An optional model enhancement that later fails will restore the exact pre-enhancement deterministic view and baseline vectors without a model call or reindex, under the same active embedding identity.
- Hydrating a span will return bytes whose hash equals the handle's digest; a tampered byte range will fail rather than return other bytes.
- A handle created at version `n` will return version `n`'s bytes after version `n + 1` exists, and will not answer `ViewStale`; a view opened at a moved head will answer `ViewStale` and be reopenable.
- A handle naming another Mind's collection, a document version the caller may not see, or a deleted document's current view will be refused or answered as not found exactly like an absent item, with no content and no existence signal.
- L0 will be ranked from document-level rows; a long document whose sections dominate a section search will not prevent a document with a matching summary from entering L0; a section search will return sections only from the documents L0/L1 selected, capped per document.
- L0 and L1 for the same bytes will be byte-identical across processes and hosts.
- An L1 response alone will be sufficient to hydrate: a client holding only that response will hydrate a section after a newer version commits, receiving the pinned bytes verified against the handle's digest and never `ViewStale`.
- A packed result will report the tokens used, the layers included, and what was truncated.
- A normal L0, L1 or L2 response will contain no internal metadata field; adding a freshness counter, a generator component, a source metadata value or a review state will change no normal response body, preview, embedding input or ranking.
- A history read will be reachable only through the history path; no search will return a historical revision.
- Same-named, same-version objects in the primary and shared collections will replay their own histories through the qualified history receiver under a validated Mind scope, while an unqualified history read returns only the primary Mind collection.
- The same shared version requested under two Mind scopes will return the snapshot only for the scope whose admitted read set and disclosure admit it, absent-like for the other; a missing scope is refused with no default.
- A history diff between versions `a` and `b` will answer as not found when either version is hidden from the caller, and will never return one side while withholding the other.

## Risks

- **L1 may omit the deciding detail.** The reader then hydrates L2, and the saving shrinks. Mitigation: the L1 first-pass closure rate is a measured gate, and the declared constraint blocks exist to put the deciding lines in L1.
- **Derived container views can be stale or too abstract.** Mitigation: they are recomputed from child versions after catch-up, their cache key names those versions, and the optional model abstract has a deterministic fallback.
- **Handle explosion.** A caller may retain thousands of handles. Mitigation: handles are small value tuples, and a stale handle is answered as not found rather than resolved by search.
- **Deleted documents.** A handle for a deleted document will not hydrate as current text, while its history stays replayable. Mitigation: the two paths answer differently and say so; deletion does not erase history.
- **Over-fetching L2.** A caller can defeat the model by asking for every span. Mitigation: the report counts hydrated bytes per task, so over-fetching shows up in the cost metric rather than hiding.
- **L1 grows with the section count.** Each section now carries a byte range, a digest and a handle. Mitigation: the format bounds a document's size, L1 reports truncation against its budget, and the added fields are small integers and one opaque handle per section.
- **Pinned hydration can outlive a grant.** A caller may hold a handle for a version it could see when the handle was made. Mitigation: a handle is not a capability — every hydration re-checks the caller's current scope for that document and version, so a revocation takes effect immediately and the answer is the same as for an absent item.
- **Token accounting.** The current estimate is a serialised-length approximation. Mitigation: the pack records a tokeniser count for the acceptance gate, and spans are counted where they are hydrated.
