# ADR: The SPOKE gaps are filled additively first, then standardised as upstream capability

Status: proposed — no carrier, receiver path, feature declaration or conformance test exists; the gap list is agreed and unimplemented
Date: 2026-11-27
Scope: Which upstream capabilities the layered Knowledge read and the write path require, which request or operation receives each in Phase 1, and what later becomes standard
Related: `2026-11-27-layered-knowledge-retrieval.md`, `2026-11-27-canonical-knowledge-format.md`, `2026-11-27-per-document-versioning.md`, `2026-11-27-machine-owned-knowledge-writes.md`, `2026-11-27-full-lifecycle-delivery-and-evaluation.md`

## Problem

A peer can neither ask for a cheaper view nor receive one. `AssembleRequest` carries only `scope`, `max_entries` and `extensions`, and its own description calls `max_entries` an entry limit hint "not enforced by protocol" (`schemas/ops/assemble-request.schema.json`). A knowledge entry's `body` is closed to summary, tags, attributes and computable maps (`schemas/data/knowledge-entry.schema.json`), so there is no skeleton and no span. `SourceAnchor` is closed with `additionalProperties: false` (`schemas/data/source-anchor.schema.json`), so a document version, a section id or a digest cannot be named on an anchor. The history face serves `get` and `prune` only (`spoke-history.md:68-69`), with an open `entity_kind`, so there is no log, no diff and no attribution. No `view_level` or `hydrate` member or operation exists in the pinned schemas or crates.

The first draft listed those gaps but did not close the receiver: it did not say which request returns L0 and L1, how a pinned handle differs from a stale current view, or how the local assembly and the native binding receive the new shapes. A gap list without a receiver is not fillable, and a peer cannot tell a host's omission from a refusal.

Two more absences matter. A commit can succeed before its response is lost, and the peer has no way to ask whether its own write landed; replaying the put is refused before the adapter, so the answer is indistinguishable from a competing writer. And the local paths — the assembling workflow and the native-binding delivery form — are not covered by a schema change that only remote peers receive.

Tenant is a different boundary from a Mind. The pinned surface selects a Mind through `scope_id` and a memory space through `space_id`; it has **no tenant selector and no tenant admission result**. An extension namespace could carry a string, but an unauthenticated string cannot authorize a repository choice. A host serving more than one tenant therefore has no safe way to decide which physical store to open, and a missing or ambiguous answer must not become a default tenant.

These are absences in the library and protocol surface, not a demand signal. A consumer cannot ask for a carrier that does not exist, so deferring the work until two consumers appear leaves the target read model unexpressible on the wire and invites each product to invent its own field.

## Proposal

The gaps will be filled in two moves: an additive Phase 1 that changes no schema, generated type or ABI, and a later standardisation that promotes the validated carriers.

**Tenant will be derived by admission, not trusted from an extension.** Admission will derive the tenant from the authenticated caller or session and return the admitted tenant to the caller. If a principal may select among tenants, it will do so through an authenticated, validated selection face (the host admission API or a product tool), never through a raw `scope.extensions.mindcore` value. The selected value will be server-issued admission state, not a second Mind-routing field. Every knowledge, history, receipt, tool and search request will then be confined to that admitted tenant, and the tenant will select the physical Git repository before any path is composed (`2026-11-27-bare-git-knowledge-store.md`) and the tenant's SQLite authority database before any Mind, collection, grant, claim, receipt, projection or history lookup. A missing, ambiguous or foreign tenant will be refused and never defaulted. Two Minds with the same `space_id` in different tenants will resolve into different repositories and cannot collide.

**Phase 1 will use only extension maps, one manifest extension and product tools, and every gap has a named receiver.** Mind selection will stay on `scope_id` and `space_id`; no Mind routing member and no second Mind-routing vocabulary will exist. The Phase 1 tenant carrier will be the **server-issued admission result** and, for a multi-tenant principal, the authenticated selection face; the raw client hint will never be a tenant selector. The later standard will carry an authenticated tenant in the session/admission result with negotiated cohort and SDK/FFI parity.

**The Phase 1 round trip will be direct, with no new operation.**

1. **L0 and L1.** `port.scope.list_knowledge_entries` will accept a set of requested layers in `scope.extensions.mindcore.view_levels`, where a single layer is a one-element set. The response will carry the requested card or skeleton in each entry's `extensions.mindcore`, and an L1 outline will carry a complete hydration handle for every section it lists. A no-hint list will keep today's response for dynamic entries and will return a document-backed entry with its card and version only, never its sections.
2. **L2.** `port.knowledge.get` will accept `scope.extensions.mindcore.span_handles[]` — the handles from an L1 outline, an earlier response, or the caller's own record — and return `extensions.mindcore.spans[]` with the text, section id, document version, byte range and digest. A handle will be **pinned**: the response will be that version's bytes or not found, and it will never answer `ViewStale`.
3. **Current views.** `ViewStale` will apply only to a view opened at a head and compiler version that has since moved — a reading of the current projection, not a pinned handle. A host that serves only the direct round trip need not expose a current view at all.

**Layer selection will be explicit, and a container will not be traversed implicitly.** Every view request will carry the set of layers it wants, drawn from `l0`, `l1` and `l2`; an `l2` request will be served as spans — by handles when the caller has them, or by an explicit section search — never as an implicit whole-document body. The response will return only those layers and will label every item with its layer. A request that names a document or a container will return that node's requested layer only and will not recurse into its descendants; returning children will require a separate explicit search or child selection, never an implicit expansion. A layer the host does not serve will be refused with a named reason — `INVALID_INPUT {reason: "VIEW_LAYER_UNSUPPORTED"}` — unless the caller explicitly asked to negotiate, and it will never be silently widened or replaced by another layer. L3 will remain the separate cold path and will not be part of this selector.

**Normal responses will carry the visible body only.** Every layer response, preview and retrieval result will carry the visible summary, navigation or outline body plus the minimum stable identifiers the next step needs — document id, version, section id, layer and byte size. It will exclude the generator component, freshness counters, source metadata, review state and every other internal metadata field. Raw metadata will be reachable only through a separate admin/debug read with its own grant, declared as its own feature, and never through a normal layer path. `2026-11-27-layered-knowledge-retrieval.md` owns which body each layer carries, and `2026-11-27-hybrid-knowledge-index-strategy.md` owns the embedding projection.

**Container L0/L1 will have a reachable receiver.** A document-list operation cannot select a folder, so Phase 1 will expose `tools.<ns>.read_container_view`. Its request will require a validated `scope_id` (or the existing admitted Scope) **plus** the container's canonical path and requested layer set; a caller with multiple Minds must name the scope, and a missing scope is refused with no default. Admission will verify the caller's `knowledge_read` grant for that Mind and use the admitted read set for that scope to compute visible children. The response will be a bounded L0 card and/or bounded L1 child navigation and key constraints, with child document ids and versions — never a fabricated container version and never an authorization fingerprint. An `l2` request on a container will be refused with `INVALID_INPUT {reason: "VIEW_LAYER_UNSUPPORTED"}` and will return no leaf content. A lower-privilege caller will receive only the children visible under its own scope. The later standard will be a container view operation with its own request/response schema and conformance cases.

**Shared stable ids will resolve through collection-qualified references.** An unqualified `port.knowledge.get`, list or history request will resolve **only** inside the primary Mind collection selected by `scope_id`. A shared or otherwise non-primary document will be addressed by `extensions.mindcore.document_ref {collection, entry_id}` — returned by search and accepted by get, hydration and the qualified history tool — from the admitted read set, the caller's Mind collection plus shared collections visible under its scope. Search will return that qualifier for every result, so every returned document is addressable exactly. The same `entry_id` may exist in a Mind collection and a shared collection; only a duplicate inside one collection is refused. The shared document is reachable only through its qualified address, the Fact keeps its unqualified address and history, and no result is ambiguous. No second Mind-routing field and no per-Mind projection copy is introduced.

**Shared writes and deletes will use the same qualified target as reads.** `port.knowledge.put` will accept `extensions.mindcore.document_ref {collection, entry_id}`; without it, the target will be the primary Mind collection selected by `scope_id`. A shared or other non-primary target will be admitted only with a write grant for that exact collection, and the pre-read, expected-base fence, publish target and receipt will all resolve that collection — no handler will infer the Mind collection for a shared target. Before any pre-read, `document_ref.entry_id` and the request's body `entry.entry_id` must be identical; a mismatch will be refused with `INVALID_INPUT {reason: "DOCUMENT_REF_MISMATCH"}` and will mutate no history, vector or row. The single validated `(collection, entry_id)` will then drive admission, pre-read, fence, publish and receipt. An unqualified put or delete cannot select a shared collection; a missing target or missing grant is refused; and the primary Mind's same-id entry and history are never touched.

**Shared history will use a qualified receiver inside an admitted Mind scope.** The pinned `history.revisions.get` dispatcher drops top-level `extensions`, and a qualifier placed in the request scope is refused before dispatch, so a shared entity cannot be addressed reliably through that path. Phase 1 will therefore expose `tools.<ns>.knowledge_history_get`. Its request will require a validated `scope_id` (or the existing admitted Scope) **plus** a `document_ref {collection, entry_id}` and the revision or version; a missing scope will be refused with no default Mind inferred from the shared collection or path. Admission will verify the caller's read grant for that Mind, and the requested version will resolve only inside that scope's admitted read set under the same per-item disclosure rule. A shared version outside that read set, or an unadmitted Mind, will answer absent-like. The tool will return the same replay snapshot shape under the document's own entity kind. The existing `history.revisions.get` will remain the **unqualified primary-Mind path** and will never resolve a shared or non-primary collection. A later standard will add a negotiated collection-qualified history reference or a history operation carrying the ref inside the admitted scope.

**Deletion will be a negotiated tool, not a put.** The pinned put pre-reads an entry and refuses a versioned request for an absent one before the adapter, and a delete carries no document body, so a put cannot be the delete path for an absent or already deleted id and its response shape cannot be relied on. Phase 1 will therefore expose `tools.<ns>.delete_knowledge_document`, declared as the `spec_delete` feature, admitted with a `knowledge_write` grant on the exact target collection and a `knowledge_read` check of the submitted document. Its arguments will be the admitted scope, the target `document_ref {collection, entry_id}`, `expected_base_revision`, a caller-supplied request id and a digest over the canonical delete request; a repeated id with another digest will answer `IDEMPOTENCY_CONFLICT`, and the receipt query will prove the caller's own request, so a dropped response is resolved from the original request without repeating the delete. It will answer the tombstone projection at its new revision — `status: deleted`, canonical name, no sections — or the existing stale code when the live version moved, and not found for an absent or already tombstoned id, uniformly with the current read. History will replay every pre-delete version and the tombstone through the qualified history receiver under the admitted scope when the target is shared, or the unqualified primary path when it is primary; the tombstone projection will carry `entry_id` equal to the envelope `entity_id` and `revision` equal to the envelope `revision`, so it satisfies the nested entity-id and revision contract. An ordinary update and a create will both be refused, so no path resurrects the id. Phase 2 will promote the tool to a negotiated delete operation whose pre-read branch accepts the delete fence and answers the same codes; until then no put-based delete is claimed.

**The later standard will add the remaining receivers.** The assembling workflow will receive L1 through a view hint on the assemble request and a view extension on the assemble packet, served by a host that composes the spec read leg; a knowledge-only host will continue to refuse assemble, as today. The native-binding delivery form will receive the scoped knowledge face before it can serve two same-named documents in different Minds, and that is an explicit later stage, not an assumption. The standardisation will also promote the receipt and history carriers below.

That change is a Mindcore change, not a SPOKE one.

**Later standardisation will promote the carriers that Phase 1 validates.** Each row will move from an extension to a schema member or operation only with its conformance cases, a version cohort, and generated parity in every SDK and the native binding. Its schedule will be set by the protocol's compatibility window, not by a consumer count.

## Alternatives considered

- **Wait for two real consumers before defining anything.** Rejected by the owner, and unsound on its own terms: a capability that cannot be requested cannot accrue consumers, so the gate would never open. The gaps are derived from the target read model and the pinned surface.
- **Extend `Assemble` now and let it be the only receiver.** Fewer carriers. Rejected: a knowledge-only host serves no assemble, the packet is a closed object, and an assembly-only path would leave direct list and get unable to return a view.
- **Define the shapes and leave the receiver implicit.** The previous draft's gap list. Rejected: a peer cannot distinguish an unimplemented view from a refusal, and no conformance test can be written against "some request".
- **A Mindcore-private wire contract.** Rejected: it would create a second Mind-routing and selection vocabulary beside `scope_id`/`space_id`, duplicate every validator, and split discovery into two stories.
- **Add the standard members now and break the wire.** Rejected: both objects are closed and generated types exist in several languages, so a new required member is a cohort-wide break with no negotiation path.
- **Keep everything in extensions permanently.** Rejected: extension payloads are shape-checked only, so no peer can validate semantics; there is no conformance suite, no parity, and no deprecation path.
- **Treat a replayed put as the receipt.** Rejected: the responder pre-reads every put and refuses a repeated create or update before the store runs, so a replay cannot distinguish "my write landed" from "someone else's did".
- **Reuse domain timeline events or forks for document history.** Rejected: document history is text authored against a document version, while a timeline event or fork is domain narrative; mixing them would make one concept answer two questions.
- **Serve layered views only through product tools.** Rejected: a peer would need Mindcore-specific knowledge to read a document, which is the private-contract failure with extra steps.

## Acceptance criteria

- A peer that does not declare the feature will receive byte-identical responses for every dynamic entry, and a collection with no document-backed entry will be byte-identical overall; an old-client conformance case will assert both.
- The Phase 1 round trip will be exercised end to end: a list requesting `l0` returns cards only, a list requesting `l1` returns cards and skeletons carrying a complete handle per section, then a get with those handles returns spans whose text hashes to their digests. A commit between the skeleton and the hydration will leave the hydrated bytes at the pinned version and will not answer `ViewStale`.
- A request for `l0` only will return no L1 outline and no L2 text, and every returned item will name its layer.
- A request naming a document or a container will return that node's requested layer only and will not enumerate its descendants; a subtree result will require an explicit search with its own limit.
- An unsupported layer will be refused with `VIEW_LAYER_UNSUPPORTED` or explicitly negotiated; it will never be silently replaced by another layer.
- A normal L0 or L1 response will contain no internal metadata field; changing a freshness counter, a generator component, a source metadata value or a review state will leave the normal body, a preview, the embedding input and the ranking unchanged.
- Raw metadata will be reachable only through the admin/debug read, which a normal read scope cannot call.
- Two sibling folders in one Mind will return separate bounded L1 navigation with no fabricated container version or authorization fingerprint; an `l2` container request will return no leaf content and a named `VIEW_LAYER_UNSUPPORTED` refusal.
- The same principal reading one shared container with two Mind scopes will receive each scope's authorized child subset; a missing scope will be refused with no default.
- No response will contain the authorization fingerprint; a high-privilege prewarm will leave a lower-privilege result unchanged.
- Two admitted Minds will resolve the same shared version through search, get, hydration and the qualified history tool from their admitted read set; an unadmitted Mind will receive absent-like results, and no second Mind-routing field will be introduced.
- With a pre-existing `spec.policy` Fact in the primary collection and a shared document of the same id, both may exist; an unqualified read will return the Fact, a qualified `document_ref` will return the shared document, both histories survive, and only a duplicate inside one collection is refused.
- From a Mind scope, an update and a delete of a shared document by qualified `document_ref {collection, entry_id}` will change only the shared document exactly once; the Mind's same-id entry and history stay unchanged. A missing shared write grant is refused, and a put or delete carrying only an unqualified id cannot target the shared collection.
- Replaying same-named, same-version objects from the primary and shared collections through `knowledge_history_get` under a validated Mind scope will return each collection's own history; the unqualified `history.revisions.get` will resolve only the primary Mind collection and will not return shared history.
- The same shared version requested under two Mind scopes will return the snapshot for the scope whose admitted read set and disclosure admit it, and absent-like for the other; a request without `scope_id` will be refused with no default.
- A put whose `document_ref.entry_id` differs from the body `entry.entry_id` will be refused before any pre-read and will mutate no history or vector.
- Admission will select the tenant's SQLite authority database before any Mind, collection, grant, claim, receipt, projection or history lookup; a principal selecting Mind `X` in tenants A and B will see independent grants, reads, writes, searches, history and receipts.
- A delete through the negotiated tool with the current live version will answer a tombstone at its new revision with no sections; the same call on an absent or already deleted id will answer not found uniformly; a current read will be not found; every pre-delete version and the tombstone version will replay with the nested entity id and revision matching the envelope; an update or create afterwards will be refused; a lost response will be resolved from the original request id and digest without repeating the delete; no put-based delete will be offered or accepted.
- A delete request replayed with the same id and a different digest will answer `IDEMPOTENCY_CONFLICT`, and another principal querying that id will answer as unknown.
- A request for `l2` with neither handles nor a query, or for a layer the host did not declare, will be refused with a named reason rather than silently downgraded or widened.
- A dropped create or update response will be resolved by the receipt lookup as `committed` without replaying the put; another principal's request for that id will answer as unknown, and an in-flight attempt will answer `in_flight`.
- A per-document stale fence will answer with the existing stale code and that document's current version; no Mind-wide value will appear.
- The later standardisation will exist as a written proposal with schema text, the assemble packet carrier, the scoped FFI path, conformance cases and SDK parity tests, tracked as planned work.
- Every row of the matrix will name its Phase 1 receiver, its later standard and the test that closes it; no row will be gated on a consumer count.
- Admission will derive the tenant from the authenticated caller/session and return it; a caller-supplied `scope.extensions.mindcore` value will not change it. A missing, ambiguous or foreign tenant will be refused and never defaulted.
- Every knowledge, history, receipt, tool and search request will be confined to the admitted tenant, which selects the physical Git repository before any path is composed; the same-named Mind id in two tenants will resolve into different repositories with no collision.
- A caller whose session admits exactly one tenant will keep today's behavior; a multi-tenant caller unable to select through the validated selection face will be refused, never defaulted. The later standard will add tenant to authenticated session/admission state with SDK/FFI parity and no second Mind routing field.
- A static check will show Mind selection still uses `scope_id` and `space_id` only; no second routing member will exist.

## Risks

- **Extension payloads are unvalidated in depth.** Peers check the namespace key and that the value is an object; inner members are unchecked. Mitigation: a version key inside the namespace, a conformance suite, and promotion to a schema once the shape settles.
- **A peer may ignore a hint.** Mitigation: a required feature is declared, and a host that cannot honour it refuses with a named reason instead of returning something cheaper than asked.
- **The direct round trip needs two requests.** L0 to L2 is a list followed by a get. Mitigation: it is the Phase 1 path by design; the assemble carrier is the later one-request path for hosts that compose it.
- **The native binding lags.** Mitigation: Phase 1 does not touch the ABI and serves the same shapes through tools; the scoped face is a named stage with its own acceptance, not an assumption.
- **The later cohort may slip.** Mitigation: Phase 1 already delivers the read model and the receipt; standardisation is planned work with its own acceptance.
- **A host may define revision semantics differently.** Mitigation: the semantics are stated normatively, pinned by conformance, and a peer that needs them requires the later capability flag.
- **Namespace ownership disputes.** Mitigation: the manifest already has a `namespaces` member; Mindcore declares its namespace there and no other product may serve it.
