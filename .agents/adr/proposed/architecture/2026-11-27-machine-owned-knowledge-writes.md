# ADR: Knowledge documents are written only through the controlled entry point

Status: proposed — no write entry, gate or export exists; the constraint is agreed and unimplemented
Date: 2026-11-27
Scope: Who may write a Knowledge document, through which path, with what validation and attribution, and how a human reviews one
Related: `2026-11-27-dual-store-knowledge-boundary.md`, `2026-11-27-canonical-knowledge-format.md`, `2026-11-27-bare-git-knowledge-store.md`, `2026-11-27-per-document-versioning.md`

## Problem

A working tree invites edits. An editor, a script or a careless `sed` can change a document without passing any validation, and the result is a state that is neither the committed version nor a validated candidate: the store cannot say what is current, and every reader has to be told which copy to trust. Editor temporary files, lock files and partial saves make the ambiguity worse, and a filesystem watcher cannot tell an intentional write from a stray one.

The current write path shows what is missing even without a working tree. `write_entry` stores whatever payload arrives, under the submitted id, with an integer revision check and no format validation (`crates/mindcore-sqlite/src/knowledge.rs:1733-1741`). There is no staging area, no cross-document invariant check, and no record of who decided the content beyond the admitted principal.

If the refactor adds files without deciding this, the first thing that happens is a human editing one, and the gate becomes advisory.

## Proposal

The Knowledge store will have no working tree, no index file and no checkout on any host. It will be created bare and will never be checked out; a human will have no path to write its files.

Every write will pass one controlled entry point, in a fixed order:

1. **Admit and resolve the target collection.** The caller's granted scope will be resolved to a Mind and a read/write grant, exactly as a served knowledge write is admitted today. A write will resolve its target collection from `extensions.mindcore.document_ref {collection, entry_id}` when present; without a ref, the target will be the primary Mind collection selected by `scope_id`. A shared or non-primary target will require a write grant on that exact collection, and the pre-read, version fence, publish target and receipt will all use it. Before any pre-read, the ref's `entry_id` and the body's `entry.entry_id` must be identical; a mismatch will be refused with `INVALID_INPUT {reason: "DOCUMENT_REF_MISMATCH"}` and will mutate nothing. A missing target or missing grant will be refused, and no handler will infer the Mind collection for a shared target.
2. **Resolve the fence.** The write will name the versions it read, one per document. A create will name no version and will mean "this id is absent", checked against an absent head ref; it will never continue an existing chain. A deletion will name the live version it deletes and append a tombstone. A content update will be refused when the named version is a tombstone: a deleted id accepts no update and no create, so no path resurrects it. The store will resolve each named version to that document's commit before validation, so validation runs against a known base (`2026-11-27-per-document-versioning.md`).
3. **Validate.** The document will be checked against the accepted format, required metadata, section ids, declared lineage and the namespace claim. The rejection set will be the format rules of `2026-11-27-canonical-knowledge-format.md` plus the lineage rules of `2026-11-27-stable-section-identity-and-drift.md`: duplicate id, reused id, a lineage `from` that is not old-only, a target that is not new-only, a section named twice, a split outside its bound, a move with an unequal fingerprint, a target in a document the operation did not name, a missing or malformed id attribute, and trailing whitespace. A retained id whose heading text or position changed will be accepted without lineage. Validation will be deterministic and will not call a model.
4. **Stage.** The attempt will first create its attempt ref with must-not-exist, carrying a live marker, and then write its candidate commit(s) under staging refs. No head will move.
5. **Check dependencies.** After staging, and immediately before the decision point — a single write's compare-and-swap, or a related operation's batch record — the store will re-read each named dependency's head and compare it to the declared version. A mismatch will discard the staged candidates and refuse the write with `DEPENDENCY_MOVED` before anything is published. This read is the exact boundary between refusal and detection: a dependency that moves **after** it is not prevented, and the write proceeds as auditable. Checking after staging is deliberate, so a dependency changed during a long staging step is still caught.
6. **Publish.** A single-document write will move that document's head by compare-and-swap. A related-document write will create one batch record under one batch ref by a single must-not-exist compare-and-swap — the decision point — then move each named head by its own compare-and-swap. Three credentials will be distinct. The **attempt credential** is one attempt ref created before staging and never deleted; a release rewrites it to a revoked marker, and it is never recreated after that. It carries a live marker and is what makes a revoked or released attempt unable to stage or publish. The **batch-decision credential** is the batch ref; the decision creates it once, retains it until settlement, and consumes no per-document credential. The **per-document publication credential** is that document's staging ref; each head compare-and-swap requires its own staging ref to hold exactly that commit and consumes only that one. A batch decision therefore leaves the credentials later document publication needs intact, while a revoked attempt cannot create or use any of them. For an operation with cross-document lineage, the lineage record will be persisted **before the batch decision ref is created**; a failure will refuse the operation on the undecided-attempt path — no batch ref, no head move, staging discarded — rather than create an irreversible decision whose bindings cannot be reconstructed. Once the decision exists, recovery will reconstruct every binding from the durable batch and lineage records without the original request. The store will not claim an all-or-none visible publication; it will report a per-document outcome (`2026-11-27-bare-git-knowledge-store.md`).
7. **Project and answer.** The derived projection will advance and the caller will receive the committed versions, the batch id when there is one, the per-document outcomes and a receipt.

A rejection will be total: a document that fails one validation rule writes nothing, and no partially valid document will be stored in a quarantine state. The response will name every violated rule with its byte range.

**Cross-document rules are checked once after staging, then detected.** A named-version rule will exist only when the writer names exact dependency versions and the rule is a function of those documents' bytes. The store will read those versions **after staging and immediately before publication**, and will refuse a dependency that has already moved; the staged candidates are discarded and nothing is published. It will **not** prevent a dependency from moving after that read — that would need a Mind-wide lock — and it will not re-validate the published document. Instead the commit will record the declared versions, and the after-publication check will open a finding naming the document, the declared versions and the dependency's current version. Rules that cannot be expressed as named versions are findings only. A write's result therefore states exactly this: refused when a named dependency had already moved at the post-staging check, otherwise published and auditable, with a later move reported as a finding.

**An uncertain outcome will be resolvable.** Every write will carry a caller-supplied request id. The store will record an authoritative write intent, and the committed commits will carry the request id, its digest and a caller proof. A negotiated, caller-authorized receipt lookup will answer `committed` when the caller's request matches **and every target it names is published**, `in_flight` while an attempt holds a live reservation **or a decided batch has not settled**, `incomplete` with the per-document outcomes when some targets are unpublished and the batch has settled, and `unknown` only when no reservation exists, no commit matches, and no attempt can still publish — which is the only state in which a resend is safe. A target will count as published when its commit is the document's current head **or an ancestor of it**; a later legitimate write therefore cannot turn a published target into an unpublished one, and the receipt will report that target's published version and commit rather than "current". **The batch status will be derived from all per-document outcomes**: `committed` only when every named target is published, otherwise `incomplete`, listing each document as `published` with its version and commit, or `unpublished` and retryable on its own. A partial success will never be reported as `committed`, and a caller will never be asked to rewrite a published document; only the unpublished ones may be retried as their own writes. The per-document outcome will be persisted in the intent **before** the batch record is removed. Another principal's request will answer as unknown, without revealing that it exists. Replaying the put is not the resolution: a repeated create or update is refused before the store runs.

**Activation, claims and their lifecycle.** Claims will be keyed by `(collection, entry_id)`, so the same id in a shared collection and a Mind collection are independent and neither can shadow the other without its own claim. The reserved prefix and type will be enabled by one activation transaction: it will insert a `legacy_occupied` claim for every existing `spec.` id in the entry and revision tables of that tenant and then write an active marker. Until the marker exists, a document write is refused and every prefixed id stays a dynamic row. After it, claims will have three states: `reserved` (an attempt holds the id and no published document exists), `published` (a document owns it, live or tombstoned) and `legacy_occupied` (an existing SQLite row owns it). A create will reserve its id in the same transaction that reserves its write. It will be refused an id with a `published` or `legacy_occupied` claim; an id held only by a live reservation will answer a retryable conflict. A successful publication will mark its claim `published` in the same transaction that records the outcome; the head-first repair below covers the crash before that transaction.

**The attempt's ownership will be one fence across both stores.** The attempt ref will be created with must-not-exist before the first staging ref and will never be deleted. Release will write it as a revoked marker **first** — creating it as revoked when the attempt never reached staging — before deleting staging refs and before marking the intent released; a resumed attempt then cannot recreate it, cannot create a staging ref, and cannot publish. That covers the attempt paused **before** its first staging ref: the revocation marker exists, so its later creation attempt fails. A release applies only to an attempt that never decided a batch; a decided batch will be completed or settled with its credentials retained, so no lease expiry can abandon it. A publication will check the live attempt marker and its own per-document staging ref, and a batch decision will check the live attempt marker and its own must-not-exist batch ref; neither consumes the other's credential.

**A published head will win over a lagging claim.** If a head exists while the claim is still `reserved` — a crash between publication and the claim update — a by-id read will treat the head as authoritative: it will route to the file store, return version 1 (or the head's version) and reconcile the claim to `published` in a short authoritative transaction. A claim will never be released while a head exists, and the recovery order is therefore head first, claim second, always in that direction. A `reserved` claim with **no** head will route no read to the file store and will be released once its attempt can no longer publish. A `published` claim will route for the document's whole life, tombstone included, so a safe retry is never blocked by its own stale placeholder and a published document is never hidden. A dynamic write will be refused the prefix unless the id carries `legacy_occupied`, in which case it continues as the ordinary row it is. No existing row is renamed, migrated or released.

**Attribution.** Each document commit will carry the admitted principal, the session, the request id and its digest, the tool or agent identity, and the compiler version. These trailers will be readable from the commit alone, so a rebuilt projection does not lose them. A client will not be able to set historical or cross-document trailers from its own payload.

**Human review is read-only.** A human will inspect a document through an export of a chosen version — the exact bytes plus a manifest naming document, version, commit and section digests — and through a read-only view. There will be no import path, because an import would be a human write by another name; the only way to change a document will be to submit a new version through the gate.

**One gate for every caller.** Served peers, product tools, workflows and maintenance jobs will all use the same entry point. A maintenance job that repairs a projection will not be allowed to write a head ref by a second route.

## Alternatives considered

- **A normal repository with a working tree, human edits and server-side hooks.** Familiar and cheap to adopt: editors, diffs and reviews already work. Rejected because hooks run after the edit, the tree can hold unvalidated bytes at any moment, and "no human edits" becomes a convention the store cannot verify. The dirty state would also have to be reconciled with the version fence, which is a second source of truth for "current".
- **A writable checkout for operators with an emergency bypass.** Viable operationally. Rejected: a bypass becomes the normal path under pressure, and the gate's rejection evidence disappears exactly when it matters. An emergency repair will instead be a normal write of the corrected document, attributed to the operator.
- **A dirty overlay over the committed documents.** Rejected: it reintroduces the two-state ambiguity the store exists to remove, and every read would need an overlay rule.
- **Documents as SQLite rows with a validation layer.** The current shape, plus the gate. Viable and simpler to deploy. Rejected because the file store is the decision of this refactor: content addressing, per-document history and byte-exact hydration all follow from it, and a validation layer over JSON payloads would still have no section spans or immutable versions.
- **Direct object writes without staging.** Fewer steps. Rejected: an agent would have no sandbox in which to compile a candidate and run cross-document checks, and a failed validation would leave unreachable objects with no lifecycle.
- **Export → edit → re-import.** Rejected as the human write it is: it would create a second authority (the edited file) and a merge question the gate cannot answer.
- **A shared publication lock so cross-document rules can be checked without races.** It would make publication-time checking complete. Rejected: it is the Mind-wide lock the owner forbids, and it would serialise unrelated documents. The two-class rule detects the residual window instead.
- **Treat a replayed put as the receipt.** No new surface. Rejected: a repeated create or update is refused before the store runs, so the replay is indistinguishable from a competing writer's win; the caller cannot learn whether its own write landed.
- **Rename legacy `spec.` rows to free the prefix.** Rejected: the store keys writes on the submitted id, so a rename is a new row; moving live rows, preimages, relations and adoption anchors risks data that works today, and every citation would change. Claims keep them reachable and reserved instead.

## Acceptance criteria

- A host will provide no writable checkout of the Knowledge store; a test will assert that opening the store never creates a working tree or index file.
- A write that violates one format rule, one duplicate section id, one invalid lineage declaration, or names a dependency already moved at the post-staging check will each be refused with the rule name and the offending byte range, and no head ref will move; an undeclared rename will not be refused, because it is classified as a deletion and an addition.
- A write that passes will publish exactly the named documents; a related-document write with one failed validation or a dependency already moved before the post-staging check will leave every named document at its previous version.
- A dependency that moves during staging will be caught by the post-staging check and refuse the write with `DEPENDENCY_MOVED`; a dependency that moves after that check will not refuse it, the write will publish and record the declared versions, and a finding will name them.
- A related-document write that fails after its decision point will report exactly the unpublished documents, and every other named document will be at its new version; no document will be reported committed before its head moved.
- A batch will answer `committed` only when every named target is published; otherwise it will answer `incomplete` with each document listed as `published` and its version and commit, or `unpublished` and retryable on its own.
- A target published and then superseded by a later legitimate version will stay listed as `published` at its version and commit, will not be offered for retry, and will not by itself make a partially published batch `committed`.
- An attempt whose staging ref was deleted before its publication will fail whole and will move no head, whether or not a new attempt exists.
- A head published before its claim was updated will be served by a by-id read, which will reconcile the claim to `published`; no read will hide the document and no release will occur while the head exists.
- A blank-line-only change outside a fence will pass; a trailing-whitespace document, a duplicate id, a reused id and an invalid lineage target will each be refused with the rule and byte range, and the same list will be asserted in the section-identity record's tests.
- Dropping a single-document response after the commit will be resolved by the receipt lookup as `committed` without replaying the put; a dropped related-document response will be resolved per its batch status, which is never `committed` while a target is unpublished. Another principal's request for that id will answer as unknown.
- A two-document batch will take one batch decision and publish both documents; the decision will consume no per-document credential, and a crash after it will resume the remaining documents while their staging refs and the live attempt marker exist.
- A decided batch will not be abandoned by credential expiry: a target whose parent is unchanged will still publish at recovery, and the batch will settle once as `committed` or `incomplete`.
- A receipt for a decided but unsettled batch will answer `in_flight`; after settlement it will answer `committed` or `incomplete`, never both, and a restart will answer the persisted outcome.
- A cross-document operation will persist its lineage record before the batch decision ref; a failed record write will leave no batch ref and no head move, and the attempt will take the undecided refusal path.
- After the decision ref exists, a crash and recovery will reconstruct every binding from the durable batch and lineage records without the original request, and will publish or settle the batch.
- A released attempt will be unable to create its first attempt ref, create a staging ref or publish; the revocation marker will be written before its staging refs are deleted, and no new attempt is needed for that.
- A stage or batch decision under a revoked attempt will answer as revoked and move nothing; a per-document publish will consume only its own staging ref.
- A create that crashes before staging, and one that crashes after staging but before publication, will both be retryable once the old attempt can no longer publish; the retry will produce exactly one root, and the old attempt will not create a credential or publish afterwards.
- After activation, a seeded `spec.` dynamic row will still be read, written and replayed from SQLite, while a document create under its id is refused; before activation, a document write is refused.
- Every committed document will expose principal, session, request id, request digest and compiler version from the commit alone.
- An export of a version will be byte-identical to the blob and will name the version, commit and section digests; no operation will accept exported bytes as a write without going through the gate.
- A grep of the repository will find one write entry: no other module will move a document head ref.

## Risks

- **No hand fix in an outage.** The gate is the only repair path, and a broken gate blocks repairs. Mitigation: the gate is pure and testable, an operator can still submit a corrected document, and the store's own maintenance does not require a document write.
- **Attribution depends on the admitted identity.** A host that admits a caller under a borrowed principal produces a true but unhelpful trailer. Mitigation: the trailer names both principal and tool identity, and the protocol's grant binding remains the authority for who could write.
- **Strictness will block legitimate content.** A writer will produce a document the grammar refuses. Mitigation: rejections are actionable (rule plus byte range), and the format is changed by an ADR, not by a gate exception.
- **Export pressures a re-import shortcut.** Someone will ask to "apply these reviewed bytes". Mitigation: the reviewed bytes are the write's content argument to the gate; there will be no path that skips validation.
- **A dependency can move between the decision-point check and the publication.** Mitigation: the check is the last read before the write, the declared versions are recorded, and the after-publication finding covers the window; closing it would need the forbidden lock.
- **A released claim could race a late attempt.** Mitigation: the attempt's staging ref is deleted in the store before the claim is released, so a late compare-and-swap fails and cannot publish; the retry's create then sees either a released claim or the retry's own root, never two.
- **A related-document write can leave a mix visible.** Mitigation: per-document outcomes, the batch id, roll-forward, and a strict capability for callers that require all-or-none (`2026-11-27-per-document-versioning.md`).
- **The receipt is an existence oracle if it is careless.** Mitigation: it requires the caller's own request id and digest, answers another principal as unknown, and never reveals a document id that the caller did not write.
- **Activation is a one-time irreversible reservation.** Mitigation: it is idempotent, it refuses nothing that exists, it runs before any document may exist, and it is not reversible by design — un-reserving an id would let a document be created under a legacy citation.
- **A decided batch holds its credentials until settlement.** Mitigation: that is the chosen terminal rule, so expiry cannot abandon it; the sweeper completes or settles it, the set of decided-but-unsettled batches is visible, and the held refs are small.
- **A lineage record write failure blocks a cross-document write.** Mitigation: the record is written before the batch decision ref, so a failure leaves no decision ref and no head move; the attempt is refused on the undecided path, and a retry re-stages and writes the record.
- **Staging objects accumulate.** Mitigation: attempt refs are retained as revocation markers and packed with cold refs, lineage records are retained per cross-document operation, staging refs carry a TTL for undecided attempts and a sweeper deletes them before releasing a reservation, and packing is a maintenance duty (`2026-11-27-bare-git-knowledge-store.md`).
