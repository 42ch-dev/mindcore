# ADR: One bare content-addressed repository per tenant, with one head ref per document

Status: proposed — no repository, provider or ref layout exists; the shape is agreed and unimplemented
Date: 2026-11-27
Class: architecture
Scope: Physical and logical layout of the Knowledge file store: objects, refs, the publication decision point, staging, compare-and-swap, library choice, maintenance
Related: `2026-11-27-per-document-versioning.md`, `2026-11-27-machine-owned-knowledge-writes.md`, `2026-11-27-derived-knowledge-indexes.md`, `2026-11-27-storage-agnostic-knowledge-seams.md`

## Problem

Storing documents as SQLite payloads gives no content addressing, no per-document immutable history and no byte-exact section hydration. Storing them in an ordinary filesystem directory gives a working tree a human can edit, editor temporary files, and an ambiguous "current" state; syncing it needs watchers or full scans.

The researched layout put one head ref per Mind (`refs/heads/m/<hex>`, report §3.7). That is superseded: one ref per Mind makes every document's chain advance on an unrelated write, so a reader of document A depends on the timing of document B's commit. The first draft of this record replaced it with one head ref per document but claimed that a multi-ref ref transaction makes a related-document write all-or-none visible. A ref transaction guarantees rollback during preparation; its publish phase is not a guaranteed all-or-nothing switch, so that claim cannot be kept.

Two mechanics also need a home in the store because they are not merely semantic: a new document's first commit has no parent and must be created against an absent ref, and a deletion must leave a version behind rather than remove a ref. Without them the store cannot distinguish "create" from "continue" or "delete" from "never existed".

## Proposal

The Knowledge store will be one bare repository **per tenant**, never one per Mind and never one global repository across tenants. A tenant is the physical isolation and backup boundary; a Mind (`space_id`) is not. The **admitted tenant** — derived from the authenticated caller/session by admission, never trusted from an extension hint — will select the physical Git repository **before any canonical path is composed**, and the tenant's SQLite authority database **before any Mind, collection, grant, claim, receipt, projection or history lookup**. A missing, ambiguous or foreign tenant will be refused and never defaulted across tenants. Each tenant will have one bare Git repository and one SQLite authority database; the Git repository will be created beside that database, never checked out, on no path a human can write. Shared and Mind-owned documents of one tenant will live in this one object store without duplication. Cross-tenant sharing will not be implicit: it will require an explicit export/import or a separately designed cross-tenant store, which is out of scope here.

- **Objects and the logical tree.** The logical Knowledge tree will be path-native: a tenant root, a collection, a domain, folders, a document and its sections. The root will be `tenants/<tenant_id>/shared` for tenant-scoped shared Knowledge or `tenants/<tenant_id>/minds/<space_id>` for a Mind-owned namespace, with the remaining components the collection, domain, folders and the document's stable id. A document will have a stable document id and a current canonical path. A document commit will hold only that document, at its canonical path in that commit's tree, and will have exactly one parent, the previous version of the same document. A root commit will have no parent. A tombstone commit will carry no document blob at the path and a `Document-State: deleted` trailer, and its parent will be the previous version.
- **Paths are part of a version, not a mapping table.** Moving a document will write a new document version whose canonical path changed. Moving a folder will write a new version for every affected document, published as a sequenced related operation (`2026-11-27-per-document-versioning.md`). No path-mapping manifest will be the primary design: the path will be content of the version and its tree.
- **A collection or folder tree is composed, never committed as authority.** A collection, domain or folder view will be composed from its document heads and the canonical path by the projection (`2026-11-27-derived-knowledge-indexes.md`). Folder metadata and declared constraints will derive from child documents and the path only; there will be no independent folder descriptor, collection-wide authoritative commit, sequence or mandatory parent commit.
- **Refs.** There will be one head ref per document, named from the collection and document identity in a total encoding. A head ref's existence will mean the document identity is occupied, live or tombstoned. There will be one **attempt ref** per write attempt, created with must-not-exist before any staging ref and never deleted: its value is a live marker until release rewrites it to a revoked marker. There will be one **batch ref** per related decision, created with must-not-exist and deleted only after settlement. There will be one **staging ref** per attempted document, created only while the attempt marker is live and consumed by that document's head compare-and-swap. There will be one **lineage record ref** per operation with cross-document lineage, `refs/mindcore/lineage/<op_id>`, pointing at a commit whose tree holds the binding manifest and retained for the life of the store. A collection's document set will be its head refs; there will be no collection snapshot ref.
- **Publication decision point.** A related-document write will first write one immutable batch record listing, for each named document, target version, target commit and expected parent, and will reference it by one batch ref created with a must-not-exist compare-and-swap. The batch ref will be created only after the operation's lineage record, when it has cross-document lineage, is durable. That single ref creation will be the only atomic step; it will require the attempt marker to be live and will neither read nor consume any per-document staging credential. Per-document head compare-and-swap will follow, in any order, each consuming only its own staging ref, and may be rolled forward by recovery. The store will not perform, and will not claim, an atomic multi-ref publish.
- **Root and create.** A first version will be published by a compare-and-swap that requires the head ref to be absent. A create against an existing head, including a tombstone, will be refused.
- **Staging.** Before its first staging ref, an attempt will create its attempt ref with must-not-exist, carrying a live marker. It will write candidate commit(s) under staging refs, one per attempted document, created only while that marker is live, and will leave every head untouched until validation and the decision point have passed. A head compare-and-swap will require the attempt marker still live and its own staging ref to hold exactly the commit being published, and will consume only that staging ref; a released attempt cannot recreate the attempt ref, so it cannot stage or publish even if it was paused before its first staging ref.
- **Attempt and batch lifetime.** A release will write the attempt ref as a revoked marker before deleting its staging refs — creating it as revoked when the attempt never created it — and the attempt ref will be retained so it can never be recreated. A **decided** batch will not be released: its attempt and staging credentials will be retained until settlement, and the sweeper will complete its remaining publications or settle it. Only an attempt that never decided a batch will be revoked at lease expiry. A batch ref will be retained until settlement and then deleted; the attempt ref stays. Commits will carry a `Batch-ID` trailer, so the audit survives the batch ref's deletion.
- **Batch settlement.** A batch will settle when every named target is published — its commit is the document's head or an ancestor of it — or is explicitly failed. It will have exactly two terminal states: `committed` when every target is published, and `incomplete` when any target is failed. A decided batch will not expire, be abandoned or be revoked before settlement; its credential TTL will not apply, because credentials are retained until settlement. Settlement will write the attempt's revoked marker and persist the settled per-document outcome in the authoritative write intent before the batch ref is deleted by the sweeper.
- **Inventory.** The authoritative discovery path for documents will be head-ref enumeration per collection. A head with no projection cursor will be adopted as a root and replayed from its chain (`2026-11-27-derived-knowledge-indexes.md`), whose cost that record states.
- **Library.** `gix` will be the recommended provider: pure-object-database read and write without a working tree, per-ref compare-and-swap, and a repository handle that can be shared across threads, at the cost of a large pure-Rust dependency tree and a recent minimum Rust version. `git2` is genuinely viable (bare init, blob and tree builders, matching-reference update) but its repository handle is `Send` and not `Sync` and its build needs a C toolchain. Neither will be relied on for an atomic multi-ref publish.
- **Maintenance.** A maintenance job will pack reachable objects, settle decided batches and delete their batch refs, run integrity checks, and verify the backup. It will never prune a live ref, so a retained staging ref of an unsettled batch and a retained lineage record stay reachable. The file store is the authority, so a backup that has never been restore-tested is a single point of loss (`2026-11-27-full-lifecycle-delivery-and-evaluation.md`).
- **Validation is not the store's job.** The store will accept bytes from the gate and move refs; format and lineage rules belong to `2026-11-27-canonical-knowledge-format.md` and `2026-11-27-stable-section-identity-and-drift.md`.

## Alternatives considered

- **One bare repository per Mind (the researched layout).** Viable, and it isolates corruption per Mind. Rejected: objects are no longer shared, every Mind needs its own handle and maintenance, a per-Mind ref either carries every document again (the rejected shared sequence) or is split per document inside every repository, and shared Knowledge would be copied into each Mind rather than referenced. Granularity is one repository per tenant, never per Mind and never global across tenants.
- **A path-mapping manifest as the primary model.** A stable id plus a separate map of current paths would keep a second source of truth for location. Rejected: a move would update a manifest and the document independently, and a rebuild would have to reconcile them. The path is part of the document version, so a move is a version, and the composed tree comes from document heads.
- **One repository per document.** Smallest blast radius. Rejected: thousands of repositories, no blob deduplication, per-document handle overhead, and no shared object cache.
- **An ordinary repository with a working tree.** Rejected by `2026-11-27-machine-owned-knowledge-writes.md`: the tree is the editable surface the design forbids.
- **A filesystem directory plus a sidecar manifest.** Cheapest to inspect. Rejected: no compare-and-swap, no immutable history, no deduplication, and sync degrades to watching or scanning directories.
- **A SQLite table of content-addressed blobs.** Attractive: one engine, one backup, one transaction model. Rejected because cross-document publication would then be a table lock or a shared sequence, there is no native pack or history DAG, and it merges the two data domains that `2026-11-27-dual-store-knowledge-boundary.md` keeps apart.
- **Rely on a multi-ref ref transaction for the batch.** Fewer objects and refs. Rejected: the publish phase is not atomic through a crash, so the store would report a success it cannot prove; the batch record gives a real decision point instead.
- **An object store as the primary backend on the host.** Rejected as primary because a host-local POSIX store is cheaper to operate; the object-store shape is kept as a provider contract (`2026-11-27-storage-agnostic-knowledge-seams.md`).
- **Shelling out to the Git CLI.** Rejected: a process and output parse per object, a runtime dependency, and a working-directory model this store does not have.

## Acceptance criteria

- Opening the store will create no working tree and no index file; a test will assert the repository directory contents after init and after a write.
- The store will create exactly one bare repository for a tenant, and a second Mind in that tenant will add no repository; a second tenant will create a second repository.
- The admitted tenant will select the physical repository and the tenant's SQLite authority database before any path, Mind, collection, grant, claim, receipt or history lookup; an ambiguous or foreign tenant will be refused, and the same-named Mind id in two tenants will resolve to different repositories and databases with no collision.
- Migration will split the current single SQLite authority database into one per tenant, preserving each Mind's registry, grants, claims, receipts and history under its owning tenant.
- Claims and document references will be collection-scoped: `document_ref {collection, entry_id}`. The same id may exist in a Mind collection and a shared collection; only a duplicate in one collection is refused. The unqualified address resolves the Fact in the primary Mind collection, the qualified address resolves the shared document, both histories survive, and a shared put or delete changes only the shared collection. A shared put or delete requires a write grant on that exact collection; an unqualified write cannot target it.
- A document commit will contain only that document at its canonical path, with the path rooted in `tenants/<tenant_id>/shared` or `tenants/<tenant_id>/minds/<space_id>` and ending at the stable document id.
- Moving a document will append a version whose path changed; moving a folder will append a version for every affected document; a folder view will be composed from document heads with no folder commit.
- A shared document and a Mind-owned document will share blobs when their bytes match, and the shared document will not be copied into a Mind.
- A first version will be created only against an absent head; a second create on the same id will be refused and will leave the head unchanged.
- A deletion will leave a tombstone commit whose parent is the previous version, with no document blob and a deleted-state trailer; the head will remain.
- Two writers on the same document from the same base will produce exactly one version; two writers on different documents will both publish.
- A failure injected after the batch ref exists and before the last head move will, after restart, show every named document at its old or new version; recovery will complete those whose parent is current; no batch will report success for a document that did not publish.
- An attempt whose staging ref was deleted before its publication will move no head, even when it already built its candidate commit, and no new attempt is needed to make that true.
- A released attempt will be unable to create its first attempt ref, create a staging ref or publish; its revocation marker is what blocks the first credential, not the absence of a staging ref.
- A two-document batch will take one batch decision and publish both documents; the decision will consume no staging ref, and a crash after it will resume the remaining document while its staging ref and the live attempt marker exist.
- A lineage record write failure will leave no batch ref and no head move; after a successful decision, recovery will reconstruct the bindings from the durable batch and lineage records.
- A decided batch whose staging credential is older than the TTL will still publish its remaining target when the parent is unchanged, and will settle exactly once; no expiry path converts it to abandoned or revoked.
- An attempt that never decided a batch will be revoked at lease expiry and will publish nothing.
- A batch decision under a revoked attempt will be refused and will create no batch ref; a per-document publish under a revoked attempt will consume no staging ref and move no head.
- After every staging and batch ref is removed and a garbage collection runs, the retained lineage record will still resolve the same successors.
- A mutual move between two documents will be built and published in either order, with no commit naming another candidate commit.
- A batch ref will not exist after settlement; its settled outcome will be readable from the authoritative intent, and its `Batch-ID` will remain readable from every published commit.
- A partially published batch will settle as `incomplete`, with its published targets at their version and commit and its unpublished ones listed for retry.
- A named target published and then superseded by a later version will not be reported unpublished, and a restart after the batch ref is removed will answer the settled outcome unchanged.
- A head with no cursor will be discovered by enumerating the collection's heads, adopted and replayed.
- Writing the same bytes twice will store one blob; identical documents across collections will share blobs.

## Risks

- **Ref count grows with documents, attempts, batches and lineage records.** One head per document, one retained attempt ref per attempt, one retained lineage record per cross-document operation, plus short-lived batch and staging refs. Mitigation: batch and staging refs settle or expire and are deleted; attempt and lineage refs are small and packed with cold refs; document heads stay loose; a lock failure is answered as retryable, never as a moved head.
- **A decided batch holds its credentials past the usual TTL.** Mitigation: that is the chosen terminal rule; retention ends only at settlement, the intent records the outcome, and the set of decided-but-unsettled batches is visible to the sweeper and measured.
- **Loose objects accumulate.** `gix` has no repository-level repack with delta compression. Mitigation: a scheduled pack of cold objects, measured, with a host `git gc` as an explicit logged fallback.
- **One repository per tenant is one blast radius per tenant.** Mitigation: integrity checks, a verified backup, a restore drill as a release gate, and no attempt to rebuild the file store from SQLite — the projection is derived, not a backup. A tenant boundary, not a Mind boundary, limits the blast radius.
- **Unpublished batch targets become unreachable.** A document that never publishes leaves a commit referenced only by the batch record until abandonment. Mitigation: settle or abandon explicitly, then let packing remove it; the intent row keeps the outcome.
- **Head enumeration costs one ref read per document per collection search and per catch-up invocation.** Mitigation: it is a directory read, measured per search and separately from document bytes, and it is the only discovery path that cannot miss a document whose cursor was never created.
- **Ref-name encoding defects.** Mitigation: a total, tested encoding with adversarial identities and a round-trip test.
