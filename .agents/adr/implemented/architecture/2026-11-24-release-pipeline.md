# ADR: Release by git-cliff changelog, version-bump PR, annotated tag, GitHub Release and crates.io publish

Status: implemented — the workspace had no way to cut a release, and the spoke channel fits once its lockstep and package-manager machinery are left out
Date: 2026-11-24

## Problem

The workspace had no release path. It carried no tags, no release workflow and no changelog generation: `CHANGELOG.md` was one hand-written `## [Unreleased]` block, and the version sat at `0.1.0` with nothing that ever moved it. Nothing identified a release for a host to pin. Cutting one by hand meant reading the commit history, writing the version section, editing the version and tagging, with nothing tying those together: the tagged commit, the range the changelog describes and the version in `Cargo.toml` could disagree and no check would notice.

The version lives in two files. All five members declare `version.workspace = true`, so their numbers are the five `[[package]]` entries in `Cargo.lock`; a bump that edits `Cargo.toml` alone leaves the lockfile stale, and CI and `CONTRIBUTING.md` run every Cargo command with `--locked`.

`42ch-dev/spoke` already runs a channel that solves this: a dispatched version-bump pull request, then an annotated tag, a GitHub Release and registry publishing on merge. It was built for sixteen version-bearing surfaces held in lockstep, for npm, crates.io, NuGet, PyPI and Maven, and for a `main` that requires signed commits. This workspace has one version surface and three publishable crates, and had no branch protection on `main`.

## Decision

A release is an annotated tag, a GitHub Release and, for a stable version, an upload of the three public crates to crates.io. `mindcore-base`, `mindcore-spi` and `mindcore-sqlite` are publishable; `mindcore-spoke` and `mindcore-runtime` stay `publish = false`, so `cargo publish` refuses them. The tag is `v<version>` on the merge commit of the version bump; the Release body is that version's section of the committed `CHANGELOG.md`.

It takes two workflows.

**New release** (`.github/workflows/new-release.yml`, `workflow_dispatch`) resolves the version, bumps it and adds the version's section to `CHANGELOG.md` on `release/<version>`, pushes one commit titled `chore(release): bump version to <version>`, and opens a pull request against `main` with the `release` label. Closing that pull request abandons the release: nothing is tagged until a person merges it. Every dispatch shares one concurrency group. Dispatching a version whose release pull request is still open only adds the `release` label to that pull request: its title, body and branch are neither pushed nor reset, so whatever was edited on it stays.

**Release** (`.github/workflows/release.yml`) runs when a pull request targeting `main` is closed, merged and labelled `release`. Its `semver-gate` job checks out the merge commit with `contents: read`, `persist-credentials: false` and `fetch-depth: 0`, and runs `node tooling/semver/check.mjs --blocking` before any tag exists — a rejected release leaves no tag behind, so the next release still diffs against the version that actually shipped. The gate is a job of its own because `cargo semver-checks` builds dependencies: with checkout's persisted Git credentials inside the write-enabled job, a compromised dependency build script could move repository refs. A prerelease version (one with a `-` suffix) is tagged and released from Git but never uploaded, so it claims no registry version and owes no compatible API to one: it skips the API diff, and only that — the migration-lock step runs for it too, because its tag ships the same migration set a stable release would. Its `release` job reads the version from `Cargo.toml` at the merge commit and takes that version's section of the committed `CHANGELOG.md` — the section the release pull request carried, curated prose included — as the tag annotation and the Release body; a version with a prerelease suffix becomes a GitHub prerelease. The section is required and has no fallback: a missing or empty one fails the job before anything is tagged, so neither a tag nor a Release is created. A rerun is safe: an existing tag must be annotated and point at the merge commit, and an existing Release is left alone. Its publish chain then uploads the three public crates, and only for a stable version: a version containing `-` skips every `verify-*`/`publish-*` job, so a prerelease is tagged and released but never claims a registry version. Merging the release pull request is what authorizes the upload — there is no second approval and no separate publish workflow. The chain is six jobs — `verify-base` → `publish-base` → `verify-spi` → `publish-spi` → `verify-sqlite` → `publish-sqlite`, ordered by `needs` so base is resolvable from the sparse index before spi and sqlite start. Verification and upload are separate jobs because the verification build runs dependency build scripts and must hold no publish credential: `env -u` strips variables only from the build's own environment, while the step's parent shell still holds `CARGO_REGISTRY_TOKEN` and the job's OIDC request variables, so a build script could read the parent environment or mint a token. Each `verify-*` job runs `tooling/release/verify-crate.sh` (`cargo publish --locked --dry-run`) under `contents: read`, no `id-token` and `persist-credentials: false`; each `publish-*` job runs `tooling/release/publish-crate.sh` with `id-token: write` and a minted token, uploading with `--locked --no-verify` so no build script shares the credential-bearing job. `publish-crate.sh` skips a version the crates.io API already answers `200` for, retries a transient registry failure at a fixed interval, and waits for the uploaded version to appear in the sparse index `cargo` actually resolves through before its job ends and the next pair starts.

`[workspace.package] version` in `Cargo.toml` is the single version source of truth. `tooling/release/bump-version.mjs` rewrites it together with the five member entries in `Cargo.lock` and the internal `version` requirement of every member manifest, so `--locked` keeps resolving. `tooling/release/next-version.mjs` owns the rule: an empty `version` input yields the next patch, a prerelease promoting to its core version; an explicit input must be strict SemVer 2.0.0 without build metadata (`+...`) and strictly greater than the current version — except before the first `v*` tag, where the current version is accepted and claimed; and a version whose tag already exists fails the dispatch before any branch is pushed.

`CHANGELOG.md` is generated by git-cliff from Conventional Commits under `cliff.toml`: Keep a Changelog groups, Morning Star process ids, plan-integration merges, release/plan/dependency chores and merge commits skipped, issue references linked to this repository. Node is used only for what git-cliff does not do: reading and bumping the workspace version (the two scripts above), and post-processing git-cliff's output. `tooling/release/render-changelog.mjs` runs on the bump branch, renders only the new section with `git-cliff --unreleased` and prepends it to the committed file, carries the hand-written body under `## [Unreleased]` into the new version's section — a full regeneration would drop it — and guarantees the section exists when every commit in range was skipped. `tooling/release/extract-changelog-notes.mjs` cuts one version's section out of `CHANGELOG.md`. The scripts import only `node:` builtins, so there is no install step; git-cliff is installed in CI by the commit-pinned `taiki-e/install-action`, and the scripts are tested by `node --test tooling/release/release.test.mjs` in the `corpus` job.

Two restrictions keep one version meaning one release:

- **Build metadata is refused.** `1.2.3+build` is valid SemVer 2.0.0, but SemVer gives build metadata no precedence, so it would equal `1.2.3` while naming another tag and another changelog heading. It fails as `Invalid SemVer` with any other malformed input.
- **A re-dispatch never resets the branch.** The bump commit is reviewed like any other, and its changelog section is meant to be edited on the pull request. Replacing the branch on each dispatch would silently drop those edits.

The spoke channel is adapted in three places, each where a spoke mechanism has nothing to act on:

- **Version.** Spoke asserts lockstep across sixteen version-bearing surfaces because five registries carry its artifacts. This workspace has one surface, so there is no lockstep assertion and no canonical `package.json`.
- **Node scripts.** Spoke's tooling runs under pnpm with git-cliff as an npm devDependency, and its release scripts also rewrite inter-crate path pins, preview breaking markers, push a GitHub-signed commit and probe registries. Here there is no `package.json`, the scripts are the four named above, and nothing is ported for lockstep, signing or multi-registry probing: one registry, reached by plain `cargo publish`, needs no probe layer beyond the sparse-index wait.
- **Inputs.** `version` is optional and defaults to a patch bump where spoke requires it. The free-text `summary` input is dropped: the Release body is the changelog's version section, and hand-written notes already have their place under `## [Unreleased]`.

## Alternatives considered

- **Port the spoke channel unchanged.** Rejected: each of its extra mechanisms needs something this workspace lacks — the lockstep assertion a second version surface, the pnpm-managed git-cliff a `package.json`, the signed-commit push a signature requirement. Its required `version` input also makes the maintainer compute the next version, and its `summary` input gives the Release body a second source beside the commits.
- **Publish from a separate manually dispatched workflow.** Rejected: this was the shape before the release job owned the upload, and it split one decision in two — the tag said released while the registry said nothing until somebody dispatched a second workflow with the same version. Keeping the two halves in agreement meant reading the tag back in the publish run, and the publish workflow could be dispatched for a version that was never tagged. It survives only as a recovery path for a stable version whose verify/publish chain failed, and a rerun of the release workflow covers that (`publish-crate.sh` skips what already exists).
- **cargo-release.** Rejected: it is unopinionated about the changelog, and its steps stop at publish, tag and push — none creates a GitHub Release — so git-cliff and a workflow would still have been written. It works as one `--execute` run that bumps, commits, tags and pushes together, which leaves no bump pull request to review; splitting it with `--no-tag --no-push` would have left it rewriting two files while the pull request, the tag and the Release were written here anyway. It publishes one crate per invocation with no wait for the registry index, which is the gate `publish-crate.sh` adds between the three uploads. It would have replaced both version scripts, and it handles `version.workspace = true` natively.
- **release-plz.** Rejected: the closest fit, and it would have replaced both workflows' shell and all four scripts. It lost on the release shape. It derives the next version from Conventional Commits and `cargo-semver-checks`, and its default workflow runs on every push to `main` to keep one release pull request updated; this channel lets the maintainer dispatch a release and name its version, patch by default. Its model is a release per package — version, changelog and tag per crate — where this workspace releases one version, one tag and one changelog. Its `git_only` mode would also have removed the upload this release now performs.
- **Keep the hand-written changelog and release by hand.** Rejected: this is the state the decision replaces. Every release would need someone to re-read the commits since the last tag and group them, while the version, the tag and the Release stayed manual steps with no mechanical link to the text. What the hand-written block does better — explaining migration and breaking impact, which a commit subject cannot — is kept by carrying the `## [Unreleased]` prose into the released section.

## Consequences

- **A human gates every release, by convention only.** The version bump and its changelog are reviewable and editable on the pull request, and closing it aborts. `main` carried no branch protection when this was implemented, so nothing forces that review, and the tag is created on the merge without waiting for the push CI that `main` runs on the same commit. The one mechanical gate between that merge and the registry is `semver-gate`'s read-only SemVer check, which is why it runs there rather than relying on CI having passed.
- **Nothing is signed.** The bump commit is a plain push by `github-actions[bot]`, and the tag is annotated but not signed. That is why spoke's GraphQL signed-commit path was not ported; a later signature requirement on `main` would reject the bump push and is the trigger to revisit this record.
- **The Release publishes what the pull request reviewed, but only what was there at dispatch.** The Release body and the version's section in `CHANGELOG.md` are the same text — the tag annotation takes it too — curated `## [Unreleased]` prose included, so an edit made on the release pull request is what the Release publishes. The section is rendered on the dispatch's base: a change merged to `main` after the dispatch is in the tagged commit but in neither the section nor the notes, and, being an ancestor of `v<version>`, in no later section either (`I-000112`). A re-dispatch does not rebuild it, because rebuilding means resetting the branch: to render the section on a newer `main`, close the pull request and dispatch again.
- **Review edits outlive the dispatch.** A re-dispatch of an open release version adds the `release` label to the pull request and changes nothing else on the pull request or the branch, so a corrected changelog section, a version fix committed there or an edited title or body is neither lost nor re-derived.
- **Changelog completeness is a commit-message discipline, not a pipeline check.** A release prepends one section rendered from commits and leaves every earlier section as committed — the first one takes the place of the hand-written `## [Unreleased]` block — and apart from the curated prose every entry is a commit subject. `filter_unconventional = true` drops a non-Conventional commit entirely, an unrecognised Conventional type lands in `Internal`, and a skipped commit is absent from both the section and the notes.
- **A stable release is pinnable from crates.io; a prerelease only through Git.** For a stable version all three public crates upload, so a consumer writes a normal `mindcore-base = "0.2"` dependency. A prerelease uploads nothing, so it is pinnable only by a `git` dependency on `v<version>`. That is the first way an outside tree can depend on an unreleased commit, something `2026-11-21-single-migration-store-bootstrap.md` did not weigh when it called the workspace unreleased; with the first stable upload its premise changes, and from then on the published migration set is owed a published compatibility policy — the SemVer policy this release stack introduces and `tooling/semver/check.mjs` enforces.
- **The registry version is claimed by the merge, and cannot be reclaimed.** Merging the release pull request with the `release` label is the authorization for the upload: there is no second approval, no separate dispatch and no dry run against the real registry. A crates.io version is immutable once published, so a bad stable release is corrected by publishing a new version, never by rewriting that one; `cargo yank` is the rollback and it leaves the name claimed.
- **The gate runs the same check CI runs, now blocking, before the tag.** `semver-gate` runs `node tooling/semver/check.mjs --blocking` on the merged commit, so the API diff against the previous stable release blocks at exactly the point where an incompatible version would otherwise become permanent, and a rejected release leaves no tag behind. It runs in its own `contents: read` job with `persist-credentials: false`: `cargo semver-checks` builds dependencies, and their build scripts must not hold a token that can write repository refs. Off a tag commit the same check stays a warning, which is what lets a breaking change land on `main` and ship with the release PR's version bump. A prerelease skips the API diff only — it never uploads, so there is no registry version whose compatibility it could owe — but the migration-lock step runs for it as well: a tagged prerelease ships the same migration set a stable release would.
- **The three uploads are ordered by the registry, not just by the workflow.** A crate's published manifest pins the registry version of the crate below it, so `mindcore-base` must be resolvable from the sparse index before `mindcore-spi` or `mindcore-sqlite` can publish. The crates.io API answers before that index does, so the script's API check alone would start the next crate too early; the script therefore waits for the version to appear in the sparse index between uploads, bounded, and fails rather than uploading a crate whose dependency is not yet resolvable.
- **The first publish happens locally; every workflow upload uses Trusted Publishing.** The three names are claimed once by a maintainer's local `cargo publish` of `0.1.0-alpha.1` with their own token. After that, each crate's crates.io Trusted Publishing entry names this repository and `release.yml`, so the workflow mints a short-lived OIDC token (`rust-lang/crates-io-auth-action`) and the repository holds no long-lived registry secret. The token is set only for the upload step of a `publish-*` job; the verification build runs in a separate `verify-*` job that holds no registry credential and no `id-token`, so a dependency build script can neither read it nor mint one — process isolation, not an environment scrub.
- **The default bump promotes a prerelease**: after `0.2.0-rc.1` an empty `version` input releases `0.2.0`, so a further release candidate must be named explicitly.
- **The version rule is code this repository owns.** Strict SemVer parsing, precedence and the bump rule are hand-written in `next-version.mjs`; a release tool would have supplied them.
- **Two one-time settings**: the repository needs "Allow GitHub Actions to create and approve pull requests", and the `release` label is created by the first dispatch.
