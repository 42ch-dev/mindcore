# Architecture: mind model and embedded persistence

## Scope

The first delivered contract of Mindcore: what a Mind is, which records carry which transition, and what the embedded SQLite store guarantees. It covers memory, personal and shared `KnowledgeEntry` storage, the cognition carrier and derived `MindState`. It excludes remote transport, capability negotiation, data movement, provider swap and caller authentication.

## Current state

- `mindcore-base` holds the transport-independent types and rules: ids (`MindId`, `SpaceId`, `ContextId`, `SubjectId`), `CallerId` (the adapter-supplied caller name the durable rows keep as attribution), the `ir` record families with their wire codec and the borrowed-transaction `MemoryRepository` boundary, the `RecallQuery` selection that boundary takes, the knowledge scope and adoption-anchor helper, and the cognition carrier helpers with `MindState` derivation. It performs no I/O.
- `mindcore-sqlite` implements `MindStore`: each opened store owns its own single-connection SQLx pool, runs the embedded migrator once (two appended files: `0001_init.sql`, carrying the ten protocol memory tables, `knowledge_entries`, `cognition_records`, `history_dedup` and `memory_embedding_vectors`, and `0002_minds.sql`, carrying `minds`), and sets WAL, foreign keys and a five-second busy timeout on that file. `knowledge_entries.history_floor_revision` is the persisted replay floor — the first revision above the newest deleted preimage, defaulting to `1` so a fresh row reads as "nothing pruned". `SqliteMemoryRepository` — the protocol repository, borrowing the caller's transaction rather than owning a pool — and the per-collection `ScopedKnowledgeStore` (implementing the pinned `KnowledgeEntryPort`) are implemented there.
- A `Mind` is a stable logical actor identity (Creator, Character); it is not a caller, a database file, a collection or a wire type. A caller is identified by `CallerId`, a plain string the embedding adapter supplies: records keep it as attribution (`requester`, `updated_by`), it is not mental state, and it decides no admission.
- A Mind is persisted and enumerable. Its id is its space's `space_id` — `MindId` holds that value and there is no second id — and the `minds` table binds the id to the knowledge collection the Mind's entries and carrier live in and to the carrier entry that holds its current judgment. A Mind owns no subject: `create` establishes none, and a write names its own. A Mind is deactivated by freezing its space and reactivated by unfreezing it; no operation archives or deletes one, and a Mind's status is its space row's. A Mind record is not a grant: it confers no access, and every operation admits the caller under its own live grants in the Mind's space.
- A served call names the Mind, never a collection. The served surface takes the request's Mind id — `space_id` on a memory request or a served workflow tool, and `scope_id` on a knowledge `Scope` once that face returns — as its only route input, and the Mind's registry row resolves it to the collection and carrier the call may reach; admission runs before any existence check, and every operation still re-derives the caller's own live grants. Stage 1 serves memory and cognition per Mind: `port.knowledge.*`, `history.*` and `knowledge.adopt` cannot name a Mind, so the surface composes none of them (`.agents/specs/architecture/serving-principal-routing.md`).
- `create`, `list` and `get` are the library entry points, `mindcore_runtime::minds` in `crates/mindcore-runtime`, over the operation and the reads in `crates/mindcore-sqlite`. `create` takes the id the caller names or assigns `spc_` and a minted identity, refuses a taken id with `InvalidInput` and `details.reason` `MIND_ALREADY_EXISTS`, and writes four rows in one `BEGIN IMMEDIATE` transaction: the space, the carrier entry `ke_carrier` in the collection `mind:<id>`, the `minds` row, and the creating principal's one grant row — `recall`, `capture`, `review`, `records_write`, `knowledge_read`, `knowledge_write` and space-wide `admin`, with no subject, no context restriction and no expiry. The operation, `mindcore_sqlite::minds::create`, borrows the caller's transaction, so a protocol operation can run it inside its own. `list` answers the Minds whose space the caller holds a live grant in, in id order; `get` answers `NotFound` for every other id. A frozen Mind is listed and read with status `frozen`.
- Memory: `capture` stages a pending candidate; candidate review consumes it, projecting one retained record (`promote`), several (`fragment`) or none (`drop`), and `dismiss` consumes it without a record. Recall reads live records only. Each mutation carries an idempotency key: a replay returns the recorded outcome instead of repeating the effect, and a second review of a consumed candidate is refused. A record keeps its candidate's placement (`space`, `subject`, context) and a repository read orders by `created_at DESC, record_id`; recall withholds a subject whose journal holds an unsettled intent.
- Memory reads authorize per operation under the caller's live grants in the space. `memory.candidates.list` with no `status` filter hides an `archived` subject and answers an empty page — the default listing is not an audit query — while a status-filtered listing is that explicit audit query and still lists the subject. `memory.records.get` is answered to either `records_read` or `recall`, and a tombstoned record additionally requires `admin`. `memory.records.list` accepts either read capability, but one grant must cover the whole selection: requirements never union across grants, so two grants that each cover part of the selection do not admit the call. `include_tombstoned` additionally requires an `admin` grant on the subject.
- `memory.recall` pages by a budget. It walks the remaining ranked records once, projecting each body only when the walk reaches it, and charges each emitted record's serialized `content` object — cognition bytes included — only while `max_bytes` is set; `max_items` bounds the count. A record is never split, and where the overflow lands decides what becomes of it. A first record that does not fit the byte budget is served whole on the current page and the cursor advances past it, while a later overflow stops the page before it and consumes nothing — the `max_items` count already reached, or a record that does not fit after the bytes already charged: the cursor resumes at it, and the next page serves that record whole. `overflow_record_id` names the record in either case, the one served or the one deferred, so every authorized record appears exactly once.
- Worked example of the budget (`crates/mindcore-spoke/tests/memory_adapter.rs`, the recall fixture with `max_bytes` 48): a record whose content is `{"text":"a"}` charges 12 bytes, the length of that serialized `content` object. A record `rec_cog` whose content adds one cognition belief charges those 12 bytes plus a cognition member larger than 128 bytes; ranked second behind a 12-byte record, it crosses this fixture's 48-byte page as a later overflow and is deferred — `overflow_record_id` names it and the first page holds only the record ahead of it. The next page then serves `rec_cog` whole and alone.
- A replay re-answers the recorded failure with its own code, message and retry class. A recorded code this build does not recognize answers one generic terminal `InternalError` with the fixed message `the recorded failure names an unrecognized reject code` and `details.reason = "unrecognized_recorded_reject_code"`: the same key can only re-play that failure, so neither the recorded message nor a `retryable` class may suggest the outcome could differ on a second attempt.
- `memory.reflections.generate` stages its receipt under a lease (`owner_id`, `lease_expires_at`). A same-key retry replays the probed receipt, with one exception: a `pending` row whose lease has already lapsed is taken over instead of answered `OUTCOME_UNCERTAIN` forever. The takeover claims the row under a fresh owner, and the lease is stamped at claim time inside the repository rather than at the request's own timestamp, because the staging transaction may sit on its basis work longer than the lease lasts. While that lease is live a further same-key retry answers `OUTCOME_UNCERTAIN` and stages nothing. Completion (`complete_reflection`, in a fresh caller transaction) inserts the envelope and settles the row with a compare-and-swap that names the lease owner exactly: only the owner the pending row is leased to may settle it. Expiry alone admits nobody — a lapsed lease still carries its persisted owner, and a takeover is the only way to change it — so a completion from a crashed owner or any other owner is refused `OUTCOME_UNCERTAIN` and the caller's rollback removes the envelope with it; the receipt stays pending until the recorded owner settles it.
- Knowledge: an entry is created with `expected_base_revision = None` only when absent, updated with `Some(revision)` only when the stored revision equals it, and the adapter assigns `1` or `stored + 1` into both the column and the payload. Every write binds the collection fixed when the port instance was constructed; refusals leave the row untouched. Revision replay reads the entry's persisted `history_floor_revision` first and refuses a positive revision below it as truncated (`details.reason` `HISTORY_TRUNCATED`) before checkpoint selection, so a pruned preimage never answers with current content; at or above the floor the selection, live fallback and positional proof are unchanged.
- Cognition: current judgment is a per-record row set under the holder's `KnowledgeEntry`. `cognition_records` stores one validated record JSON per row keyed `(collection, entry_id, append_seq)`, and `knowledge_entries.cognition_head_seq` is the single current-judgment pointer with a composite foreign key back to that row; `NULL` means no records yet. An append reads the carrier header without hydrating history, compares the expected carrier revision, validates the record (holder, view, integer `order`), inserts one row and advances head plus outer revision in the caller's transaction. Full DTO reads reconstruct `modules.cognition.records` from one SQLite snapshot in `append_seq` order; an absent module stays absent, a present empty array stays empty. A stored record is accepted only when its holder is exactly `{kind: "knowledge_entry", namespace: "mindcore", id: <carrier entry id>}`. `MindState` is derived from the carrier's authorized revision and is never persisted. Details: [`data/cognition-record-storage.md`](../data/cognition-record-storage.md).
- A present `modules.cognition` module is validated at the single persistence boundary (`put_knowledge_entry`) before the write reservation, and every appended record is validated by the storage append (`append_cognition`) on the caller's transaction, so no path can commit an invalid carrier.
- A present `order` on a stored cognition record must be written as a JSON integer representation: the pinned `BeliefOrder` type reads `i64` only, so `1.0` (or any non-integer number) is refused at the same carrier boundary — append and `put_knowledge_entry` share this rule, and the generic IR codec is not narrowed.
- A deliberation attempt projects into one SPOKE `Judgment` (`spoke-judgment`, schema version `1`) in `crates/mindcore-spi/src/judgment.rs`: the workflow builds it from values the attempt already holds and validates it with the released `validate_judgment_typed` before returning it, so no response carries a judgment the validator refuses. `judgment_kind` is `mindcore:deliberate`; `target` is the request's cognition target as `{kind, id, namespace}` with no `revision`; `evidence[]` is exactly the cited memory records, one `memory_record`/`mindcore` reference per cited entry with that entry's stored positive revision, empty when nothing is cited; `verdict.outcome` is `mindcore:<status>` for the attempt's own branch (`no_change`, `needs_review`, `settled`), `verdict.detail` carries the verdict's `recommendation`, `evidence_ids` and `record_ids`, and `basis` is the verdict's rationale. No confidence is written, because the verdict carries none.
- `judgment_id` is `jd_` plus the JCS SHA-256 of `{principal_id, space_id, subject_id, holder, target, status, verdict}`: equal attempt content yields an equal id, and another branch or another verdict yields another. `created_at` is the workflow clock read once where the judgment is built and enters no digest. The projection reads no store, so a cited entry that carries no stored revision is refused rather than given a derived one.
- The subject of a judgment is optional. The served `deliberate` names one and takes the subject-level path — its snapshot recall, its grant re-check and its unsettled-intent check run over that subject; a facade `deliberate` names none, skips the snapshot recall (a verdict cites evidence and existing cognition records only, and a `record_ids` entry naming a memory record is refused), requires a space-wide live `recall` grant and withholds while any intent in the space is unsettled. An absent subject enters the `judgment_id` digest and the record id digest as `null`. A facade `deliberate` stamps the Mind's id as the record's `assessment_context.context_id` — one component of the record's compound item identity — while the served path derives it from the subject when the request names none, and a request naming neither context nor subject is `InvalidInput`.
- The facade is `mindcore_runtime::Mind` (`facade.md`): one handle per Mind whose `open` is one registry read and whose operations compose the existing adapter, ports and workflows — `capture`, `review` (the publish-before-commit fold), `recall`, `knowledge_get`/`put`/`list`, `cognition_read` and `deliberate` — each opening its own transaction and admitting the caller under its live grants on it. It adds no write path: memory writes go through the adapter, knowledge writes through `write_entry` with its single cognition validation, and no operation accepts a collection, `owner` or `viewpoint` from the caller.

## Invariants

- Each opened `MindStore` owns one pool and runs one migrator against the database file it was opened on; exactly one store per file is the caller's obligation, and two stores on one file are unsupported rather than refused.
- A mutating operation takes the SQLite write reservation (`BEGIN IMMEDIATE`) before reading claim or revision state.
- A candidate is not recallable before review; a rejected write changes neither payload nor revision.
- An entry is resolvable only through a port bound to its own collection, even when two collections hold the same raw `entry_id`; no API accepts a caller-supplied collection, `owner` or `viewpoint` as a selector.
- Only an explicit carrier update changes the current judgment; adoption, a shared-content change and a read never do. Appending preserves the previously committed records byte-for-byte.
- A returned judgment is one the released validator accepted at build time, and on the `settled` branch it is built and validated, and the record serialized, before the last deadline check; `commit_cognition` follows that check, so a projection defect refuses while nothing is written. The request deadline also reaches `commit_cognition`, and its refusal applies only where an expiry is observed: while the settle waits for the store connection, or on a connection already in hand before `BEGIN IMMEDIATE` — either observation answers the deadline refusal and starts no write. The bound stops at the begin: the wait for SQLite's own write lock inside `BEGIN IMMEDIATE` is outside the request deadline and can outlast it, and a write that has begun keeps its actual or uncertain outcome, which may land after the deadline.
- `ScopedKnowledgeStore` keeps the caller's timestamp values in the `KnowledgeEntry` payload without that memory round-trip refusal; the store encodes only its separate SQL bookkeeping columns. Raw timestamp spelling is not a guarantee of the typed knowledge port — wire fidelity belongs to the IR codec (`storage-ir-boundary.md`).
- A Mind is written by one `BEGIN IMMEDIATE` transaction or not at all: a failure in any of its four writes leaves no space, carrier, registry or grant row.
- A registry row names an existing space and an existing carrier entry: `minds` carries a foreign key to each.
- No operation removes a Mind or its registry row; deactivation is the space's `frozen` status.

## Change obligations

- Changing the schema, a table, or the migration ownership requires updating this page in the same change and proving reopen behaviour.
- Changing a write path must keep the write reservation before any claim read and must not add a second validation point for the cognition module.
- Changing the carrier shape or the derivation requires updating this page and the SPOKE validator usage together.
- Adding a caller-controlled selector to any storage API is a contract change: it must be rejected or this page must record the authorization model explicitly.
- Changing the `minds` table, `create`'s four writes, the visibility rule of `list` and `get`, or the entry points requires updating this page in the same change.
