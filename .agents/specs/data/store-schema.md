# Data: store schema and migration policy

## Scope

The SQLite schema a host gets from `MindStore::open`. The page states the schema the embedded migration set produces — the published files plus any file appended since the last release — and how a database written by an earlier set reaches it; which files are published is `tooling/migrations/migrations.lock.json`, and the upgrade rules are `docs/storage-compatibility.md`. It does not define protocol semantics (those live with the adapter and repository) or persistence for remote faces.

## Current state

`crates/mindcore-sqlite/migrations/` holds two appended files, `0001_init.sql` and `0002_minds.sql`. Together they create:

- the fourteen protocol memory tables — `memory_spaces`, `memory_subjects`, `memory_grants`, `memory_candidates`, `memory_records`, `memory_receipts`, `memory_journal`, `memory_profiles`, `memory_reflections`, `memory_provider_meta`, `memory_exports`, `memory_export_chunks`, `memory_imports`, `memory_import_chunks` — with the column names, types, `CHECK` clauses, `WITHOUT ROWID` declarations and indexes that `SqliteMemoryRepository` and the transfer module decode;
- the four transfer-plane tables. `memory_exports` is one committed export: `export_id` primary key, `space_id`, `requester_principal_id`, nullable `subject_id` (`NULL` for a whole-space export) and `selection_json` (the canonical `ReadSelection`, with `CHECK (selection_json IS NULL OR subject_id IS NOT NULL)`, so a selection without a subject is unreachable), `include_tombstoned IN (0, 1)` for the admin recheck a later page read performs, a 64-character `bundle_digest`, `chunk_count >= 1`, and `created_at`/`expires_at` fixed at creation and never reset by a replay or a page read, plus `state IN ('live', 'expired')` — the persisted expiry decision a reclaim writes, so a page read answers `EXPORT_EXPIRED` from the row rather than from a clock that may have rolled back. It stores metadata only: no whole-bundle blob is duplicated. `memory_export_chunks` stores each complete immutable wire chunk keyed `(export_id, ordinal)` with `ordinal >= 0` and a non-empty `payload`; ordinal zero carries the header. An `(expires_at)` index drives the export expiry decision: every successful transfer write of a space marks that space's expired exports `expired` and releases their chunks, while the header stays so a later read still answers `EXPORT_EXPIRED`. `memory_imports` is the single live staging row per source export: `import_id` primary key, target `space_id`, `requester_principal_id`, `source_export_id`, the `bundle_digest` and `expected_count` fixed by ordinal zero, the durable `next_ordinal` (`BETWEEN 0 AND expected_count`), `conflict_policy IN ('fail', 'rename_subject')`, `adopt_grants_json`, `reference_translations_json` (ordinal zero's translation pairs, applied to transferred content at staging), `state IN ('staging', 'staged', 'activated', 'discarded', 'expired')`, the translated `staged_payload_json`/`staged_report_json` frozen by final verification, `provenance_json`, `created_at`/`expires_at` and `activated_at`, with `CHECK ((state = 'activated') = (activated_at IS NOT NULL))` and `CHECK (state NOT IN ('staged', 'activated') OR next_ordinal = expected_count)`. A unique partial index on `(space_id, requester_principal_id, source_export_id) WHERE state IN ('staging', 'staged')` makes the tail-chunk lookup single-valued — the wire tail carries no import id — and holds one live import per source export across both non-terminal states, so a second idempotency key cannot open a second import that would activate the same export twice. An `(expires_at)` index drives the expiry decision: every successful transfer write of a space reclaims that space's expired rows to the content-free `expired` state and releases their payload and chunks, so a later stage of the same source export starts a fresh sequence. `memory_import_chunks` keys each accepted inbound chunk by `(import_id, ordinal)`; final verification consumes and removes them, and activation applies the frozen `staged_payload_json` instead of re-reading them. No foreign key joins the four tables to each other or to the older ones: the composite primary keys already carry the association, matching the rest of the protocol schema, and chunk-row immutability is write discipline rather than a trigger because the host-only `immutable_*` triggers stay out of this set;
- `knowledge_entries` then `cognition_records`, two tables that reference each other: the entry's composite foreign key from `cognition_head_seq` points at the record primary key, and each record points back at its entry. Neither orders the other, and `knowledge_entries` is created first, so its cross-reference is a forward reference SQLite accepts without resolving at creation time. `knowledge_entries.superseded_by TEXT` is the nullable liveness marker: its composite foreign key `(collection, superseded_by)` references the entry primary key, so a marker can only name an entry of the same collection, and no cascade removes a successor. Its `NULL` means current; an ordinary payload write never sets or clears it. `knowledge_entries.history_floor_revision INTEGER NOT NULL DEFAULT 1 CHECK (typeof(history_floor_revision) = 'integer' AND history_floor_revision >= 1)` is the first revision above the newest deleted preimage — the earliest revision the entry can still answer: explicit pruning advances it, and every new row starts at `1`, so "nothing pruned" needs no back-fill. `cognition_records.append_prior_shape` is `NULL` for a record a full-entry put committed and, for a dedicated append, classifies what that append replaced: `0` the module kept `records`, `1` the module was absent, `2` the module existed without `records`. A partial index, `idx_knowledge_entries_live` on `(collection, entry_id) WHERE superseded_by IS NULL`, serves the live listing: the collection's current rows are read in `entry_id` order from the index alone, so retired rows are never scanned for that page;
- `knowledge_entry_revisions`, the preimage of every revision a full-entry update displaces: one row per `(collection, entry_id, revision)` holding the replaced payload, its cognition head and the instant that state was written (`recorded_at` copies the replaced row's `updated_at`, not the instant it was displaced). A `BEFORE UPDATE OF revision` trigger on `knowledge_entries` — `knowledge_entries_capture_revision` — inserts it, and skips only a dedicated cognition append — the head advanced by exactly one and the record now indexed by it carries a non-null `append_prior_shape`. A full put, even one whose head advances by one, saves its preimage. There is no conflict suppression: a replayed revision assignment surfaces as a constraint failure instead of overwriting history. The parent key is non-cascading, so an entry holding history is never deleted out from under it; an explicit `prune_history` deletes the checkpoints below the kept window and advances the entry's `history_floor_revision`, and nothing else removes a row;
- `history_dedup`, the served history's prune dedup record: one row per retry identity, `namespace TEXT NOT NULL` (the collection its history surface routes to), `key TEXT NOT NULL` (Connect's retry key), `principal TEXT NOT NULL` (the requester the key names), `payload_digest` and `outcome_json`, with `PRIMARY KEY (namespace, key)`, `CHECK ((payload_digest IS NULL) = (outcome_json IS NULL))` and `WITHOUT ROWID`. The namespace is a column rather than a prefix inside `key`: a collection name is arbitrary, so no separator makes a framed string unambiguous, and the capacity count needs an exact namespace equality instead of a prefix range. `principal` makes the quota per caller: it is not derivable from `key` in SQL, so `lookup` and `record` store it from the retry identity's third member, and every key that does not parse — unparsable, truncated, a non-string member — is charged to one shared `unknown` bucket instead, so such keys cannot mint fresh quotas. A row inserted with both payload columns `NULL` is a claim; `record` fills both in one upsert, so a second record for a key replaces the first. Nothing orders or expires rows and the table carries no timestamp column — no clock is read and nothing deletes — but each `(namespace, principal)` pair is capped at 4096 rows: a claim past the bound inserts nothing, so a fresh key answers `RECEIPT_EXPIRED` and `record` grows no quota beyond it. The bound is per principal inside the collection's namespace, so every surface serving one collection shares that collection's namespaces while each caller holds its own quota. `idx_history_dedup_principal` on `(namespace, principal)` serves both quota counts — the claim gate and `record`'s guard — as a covering-index seek: the primary key is `(namespace, key)`, so without it the count would seek the namespace and filter `principal` over every key the collection holds.
- `memory_embedding_vectors`, keyed `(record_id, identity_hash)` with the record revision, dimension and little-endian `f32` bytes, plus the identity index.
- `minds`, the Mind registry, created by `0002_minds.sql` — one row per Mind, keyed by `space_id`, because a Mind is one memory space and the row's key is the space's id; `knowledge_collection` and `carrier_entry_id`, each `TEXT NOT NULL CHECK (length(..) > 0)`; `WITHOUT ROWID`; two foreign keys that do not cascade, `space_id` to `memory_spaces(space_id)` and `(knowledge_collection, carrier_entry_id)` to `knowledge_entries(collection, entry_id)`; no column for what the space row already states (display name, status, creation time); no index, because the read that lists Minds filters `memory_grants` by principal and joins `minds` on its primary key; `idx_memory_grants_principal_space` is available for the grant lookup.

`MindStore::open` applies the embedded set with `PRAGMA foreign_keys` on, so every foreign key is enforced from the first write. `minds` is created by the second file, so both of its foreign keys reference tables the first file created. The set's one forward reference, `knowledge_entries` naming `cognition_records`, resolves when that table is created, since no row can be written before the migration finishes. The protocol memory tables carry no fixture-only foreign keys: the Nexus writer guards, outbox/immutability triggers, `nexus_writer_*` UDFs and the three `core_*` tables remain caller-owned and are not installed here.

There is one schema source. Tests open a temporary database through `MindStore::open` and seed rows; no test file declares `CREATE TABLE` for a table `open` creates. SQLx preparation reads the same migration into an empty file.

## Migration policy

The published set is `tooling/migrations/migrations.lock.json`; `0001_init.sql` shipped in `0.1.0` and is immutable. A schema change appends a file named `NNNN_<description>.sql` whose prefix follows every locked one, and `0002_minds.sql` is the first such file; an appended file may merge before its lock entry exists, and it becomes published when the release pull request adds that entry, before the release is tagged. `MindStore::open` applies the appended files in order to a database recorded at an earlier set, so a database written by `0.1.0` reopens with its records. The accepted applied sets, and the rule that `open` never repairs, downgrades or converts a database, are `docs/storage-compatibility.md`.

`MindStore::open` refuses a database whose applied set no longer matches, with three distinct shapes:

- `VersionMissing(n)` — the database applied a version the embedded set no longer contains.
- A migration checksum mismatch — the applied version is still embedded but its SQL changed.
- `ExecuteMigration(<version>)` — the schema is present but a recorded version is not, so the pending file reruns over tables that already exist.

All three mean recreate. A busy or locked database, an I/O error or a permissions problem is not a migration mismatch: fix the cause and retry; never delete a valid file.

## Invariants

- One schema source: the migration. Tests seed data, never tables.
- The production open path is the only way a test obtains the schema, so a regression in the migration fails the end-to-end test instead of passing through a fixture that supplies the missing table.
- A history preimage is written by the update that displaces it, in that update's transaction: a refused, stale or rolled-back write leaves none.
- The liveness marker is storage-owned and only a marking update writes it: a payload write can neither forge nor clear it, and every marking update advances the source revision, so the revision trigger saves its preimage like any other displaced state.
- `revision` and `cognition_head_seq` are signed SQLite integers: a writer refuses a next revision it cannot represent before writing any row, so every committed revision stays addressable by the preimage table and replay.
- Saved preimages and committed cognition records are immutable; replay reads them and never rewrites them.
- A migration change and the code that reads it land together; an intermediate state where the schema moved and the readers did not is not a deliverable.
- Column names, types and constraints are shared with the borrowed-transaction repository; changing one without the other breaks decoding at runtime, not at compile time.
- A `minds` row exists only beside the space and the carrier entry it names, and nothing deletes a Mind, so neither foreign key needs a cascade.
- A Mind's status is its space row's `status`, and the registry holds no state of its own.

## Where it lives

- The whole embedded set: `crates/mindcore-sqlite/migrations/0001_init.sql` and `crates/mindcore-sqlite/migrations/0002_minds.sql`, applied in order by `MindStore::open` in `crates/mindcore-sqlite/src/store.rs`.
- Readers of the tables it creates: `crates/mindcore-sqlite/src/repository.rs` (`SqliteMemoryRepository`, the ten older `memory_*` tables), `crates/mindcore-spoke/src/transfer/` (the four transfer-plane tables, plus the subject and content-free receipt scans the bundle builder performs), `crates/mindcore-sqlite/src/knowledge.rs` and `crates/mindcore-sqlite/src/cognition.rs` (`knowledge_entries`, `cognition_records`), `crates/mindcore-runtime/src/history_dedup.rs` (`history_dedup`, through the pool `MindStore::pool` hands it), `crates/mindcore-sqlite/src/vectors.rs` (`memory_embedding_vectors`), `crates/mindcore-sqlite/src/minds.rs` (`minds`).
- Open-path tests that seed rows through `MindStore::open`: `crates/mindcore-sqlite/tests/store_bootstrap.rs` and the seed helpers beside them.
- `crates/mindcore-sqlite/tests/minds.rs`, and `crates/mindcore-sqlite/tests/store_migrations.rs`, the latter proving that the appended file applies to a database written by the previous published set.
- Decision records: `.agents/adr/implemented/architecture/2026-11-21-single-migration-store-bootstrap.md`, and `.agents/adr/implemented/architecture/2026-11-25-mind-is-one-memory-space.md`, the decision record of the registry and the appended file.

## Change obligations

A migration edit lands together with this page, the reader that decodes the changed table, and the tests that open the database through `MindStore::open` — a schema without its reader, or a reader without its schema, is not a deliverable. An appended migration lands together with this page, the reader that decodes its table and the open-path test that proves a database written by the previous published set reopens through it; its lock entry is written by the release pull request that ships it, before its tag; and changing the published set, or the three refusal shapes `open` reports, changes this page in the same commit.

## Adoption anchor storage

Adoption writes a copy of a shared entry into the served destination collection, carrying the protocol's `KnowledgeEntry.adoption_anchor`. The destination slot, not the source id, decides where the copy lands: the copy's `entry_id` is the request's `destination_entry_id` when supplied — which may be the resolved terminal's own id — and that terminal's id otherwise. Storage-wise the anchor is a field inside `knowledge_entries.payload`, so the schema gains no column for it; no legacy `extensions` encoding is read or written, and a database written by an earlier published set reopens through the appended files, while `MindStore::open` refuses a set it cannot reconcile rather than recreating the database. The immutable-anchor put rule belongs to `.agents/specs/data/knowledge-lifecycle.md` § Adoption; the destination default, the terminal resolution and every served refusal rule belong to `.agents/specs/architecture/serving-seam.md`. This page keeps only what the schema itself must guarantee: no column, index or trigger serves adoption.

`mindcore_base::knowledge::adoption_anchor` is the shape's single builder and `adoption_anchor_parts` its single parser; the SQLite resolver reads back through that parser rather than owning a second copy. The schema itself changes nothing for adoption: no column, index or trigger is added or removed, and the served `knowledge.adopt` operation writes through the same `knowledge_entries` put path as any other create.
